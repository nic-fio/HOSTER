Dentro hoster

Tutto quello che serve per capire, costruire, provare e modificare hoster: architettura, resolver XFileSharing, motore di download, ripiego TLS, estrazione, interfaccia da terminale, test e convenzioni del progetto.

Versione 1.0 Linguaggio Go 1.24 Dimensione ~2.900 righe di Go, più ~1.100 di test Dipendenze solo rardecode

Sommario

Premi / per cercare. L'indice analitico elenca file, funzioni e argomenti. I riferimenti file.go:riga puntano alla versione 1.0.

Panoramica

Cos'è hoster visto da dentro, i principi che l'hanno guidato e la mappa del codice.

Cosa copre questo manuale

Il manuale utente spiega cosa fa hoster; questo spiega come. Dopo averlo letto dovresti sapere dove mettere le mani per adattare il resolver a un sito nuovo, cambiare il motore di download o l'estrazione senza rompere il resto, e verificare le modifiche. Si dà per scontato che tu conosca Go e le basi di HTTP. Il perché delle scelte è in decisioni e storia.

Principi

1

Un solo binario

Eseguibile statico (CGO_ENABLED=0), nessun programma esterno obbligatorio. Unica libreria: rardecode.

≡

Un resolver per tutti

I siti XFileSharing condividono lo stesso script lato server: una logica generica con euristiche li copre quasi tutti.

☑

Solo premium

Nessun aggiramento di captcha o countdown: se il countdown compare, l'errore lo dice.

↺

Robusto sul campo

Ripresa senza duplicazioni, controllo della dimensione, link scaduti rigenerati, TLS tollerante solo dove serve.

✓

Test senza rete

47 test ermetici con server HTTP fittizi; il test dal vivo parte solo se richiesto.

?

La documentazione è codice

make test fallisce se un'opzione o un file non sono documentati o se la versione non coincide.

$ make

$ make dist

Su Debian 13 il pacchetto golang-go è già la 1.24. Con un Go più vecchio ma almeno 1.21, la direttiva go 1.24 di go.mod fa scaricare in automatico il toolchain giusto. La prima build scarica rardecode nella cache dei moduli.

CI e release

La CI (.github/workflows/ci.yml) gira a ogni push su main e a ogni pull request: installa Go dalla versione di go.mod, esegue make test e make dist e conserva i binari. Su un tag v* un secondo job crea la release GitHub con i due binari e SHA256SUMS; il messaggio del tag annotato diventa la descrizione.

  1. Aggiorna la versione in help.go ("hoster 1.0"), README.md, docs/index.html e nei due manuali. make test controlla che coincidano.
  2. git tag -a v1.1.0 -m "hoster 1.1.0: …novità…"
  3. git push origin main v1.1.0

Recupero e backup

Il repository è progettato perché un git clone basti a riavere tutto, tranne i file personali. Il programma pronto è già dentro (./hoster); per ricostruirlo e verificarlo:

$ git clone https://github.com/nic-fio/HOSTER.git
$ cd HOSTER && tools/setup-dev.sh --install && make test

tools/setup-dev.sh imposta anche l'identità git locale (nic-fio con l'indirizzo noreply di GitHub), che non viene clonata perché sta in .git/config. tools/backup.sh DIR crea hoster-AAAA-MM-GG.bundle, verificato con git bundle verify, e avvisa se ci sono modifiche non registrate o commit non ancora spinti su GitHub.

Il punto chiave è il cookie jar condiviso: il resolver fa il login e ottiene i cookie di sessione; il client di download (newDownloadClient, download.go:63) riceve lo stesso jar, quindi scarica con la stessa sessione. Anche lo User-Agent (-U) è lo stesso per entrambi, perché alcuni siti legano la sessione all'UA.

Un'esecuzione

sequenceDiagram
  participant M as main
  participant R as Resolver
  participant S as Sito
  participant D as Downloader
  M->>M: legge account e links
  loop per ogni lotto di -j link
    loop per ogni link del lotto
      M->>R: Resolve(link)
      R->>S: login (solo la prima volta per host)
      R->>S: GET pagina-file
      S-->>R: file diretto oppure HTML
      R-->>M: Resolved{URL, Name, Link}
    end
    par un goroutine per file
      M->>D: downloadFile(URL, dest, refresh)
      D->>S: sonda Range 0-0, poi GET
      D-->>M: ok / errore
    end
  end
  M->>M: riepilogo, poi estrazione se -e

Il ciclo in main.go procede a lotti di -j link: risolve tutti i link del lotto in sequenza, lancia un goroutine per file e aspetta la fine dell'intero lotto (sync.WaitGroup) prima di passare al successivo. Così i link diretti vengono generati poco prima dell'uso, perché scadono in fretta. Il rovescio della medaglia: un file lento tiene fermo il lotto successivo.

Prima di lanciare un download, main calcola la destinazione (Name, o fileNameFromURL se vuoto) e la segna in seenDest: un secondo link verso lo stesso file viene saltato come duplicato. La funzione refresh passata al downloader richiama Resolve sul link originale (Resolved.Link) quando il link diretto scade.

Dove va l'output

Barre, righe di log e riepilogo del download vanno su stderr; la riga scaricati: N falliti: M, l'uscita di --dry-run e quella dell'estrazione vanno su stdout. Gli errori fatali (fatal, main.go:227) vanno su stderr con il prefisso hoster: e stato 1. Il pacchetto flag esce con stato 2 sulle opzioni sconosciute, stampando la guida in testo semplice (flag.Usage = usage).

Account e link

Il formato dei due file di ingresso e come vengono abbinati gli account ai link.

Formato di account

LoadAccounts (accounts.go:45) legge una riga per volta, dopo TrimSpace, e salta righe vuote e commenti #. firstSep trova il primo tra : e ;: il primo separatore chiude il dominio, il secondo l'utente, e la password è tutto il resto, non ripulito (può contenere separatori e spazi interni). Il dominio passa da normHost, l'utente da TrimSpace. Una riga senza separatori, con un solo separatore, o con dominio/utente vuoti dà un errore con il numero di riga.

Abbinamento host ↔ account

Ogni account è indicizzato due volte: per host normalizzato (byHost) e per etichetta, la parte prima del primo punto (byLabel). Lookup prova prima l'host esatto, poi l'etichetta: così terabytez:… vale per terabytez.org e terabytez.com.

normHost (util.go:17) accetta anche un URL intero: minuscolo, toglie schema, percorso, query, credenziali, porta e www.. Attenzione: labelOf prende la prima etichetta, quindi un sottodominio come fs12.terabytez.org dà fs12. Non è un problema perché il lookup avviene sull'host del link della pagina-file, non su quello dei server di download.

Formato di links

LoadLinks (links.go:11) salta righe vuote e commenti, toglie gli spazi ai bordi e deduplica mantenendo l'ordine. Il buffer dello scanner è di 1 MB per riga. Non c'è validazione: un URL non valido viene segnalato da Resolve.

Il resolver

Il cuore di hoster: login XFileSharing e trasformazione di una pagina-file in un link diretto, con il nome vero del file.

Il client del resolver

NewResolver (resolver.go:33) crea un cookie jar e un http.Client con timeout totale di 90 secondi (fisso, indipendente da --timeout) e trasporto newTLSFallbackTransport. do imposta User-Agent e Accept e legge al massimo 16 MB di corpo. Il client segue i redirect (comportamento predefinito di Go) e il jar raccoglie i cookie di ogni passo.

Login

sequenceDiagram
  participant R as Resolver
  participant S as https://host
  R->>S: GET /?op=login
  S-->>R: pagina di login + cookie iniziali (+ token)
  R->>S: POST / op=login, login, password, redirect[, token]
  S-->>R: pagina risultato + cookie di sessione
  R->>R: looksLoggedIn?

ensureLogin (resolver.go:142) esegue il login una sola volta per host: il mappa loggedIn è protetta da mu, perché le ri-risoluzioni dei link scaduti avvengono in parallelo. L'host è sempre contattato in https. Se nella pagina di login c'è un campo nascosto token (CSRF), viene inviato.

looksLoggedIn (resolver.go:187) è un'euristica:

  1. se la pagina contiene incorrect login, wrong password o username and password do not match → fallito;
  2. se contiene op=logout, logout, my account o myaccount → riuscito;
  3. altrimenti riuscito se nel jar c'è un cookie xfss, xfsts, login o con sess nel nome.
Limite

L'euristica è permissiva: basta la parola «logout» in qualunque punto della pagina, o un cookie di sessione anonima, per dichiarare il login riuscito. Un login in realtà fallito si manifesta dopo, come «countdown rilevato» o «link diretto non trovato».

Risoluzione

flowchart TB
  A["Resolve(link)"] --> B["ensureLogin(host)"]
  B --> C["openFilePage: GET, guarda solo le intestazioni"]
  C -->|"non text/html, o attachment"| D["file servito direttamente:<br/>URL = link originale"]
  C -->|"HTML"| E["extractDirectLink(pagina)"]
  E -->|"trovato"| F["Resolved{URL diretto}"]
  E -->|"no"| G["passi 2..4: countdown? form con op?"]
  G -->|"countdown"| X1["errore: non premium"]
  G -->|"form"| H["POST del form, extractDirectLink"]
  H -->|"trovato"| F
  H -->|"no"| G
  G -->|"nessun form"| X2["errore: link diretto non trovato"]

openFilePage (resolver.go:103) apre la pagina-file e decide solo dalle intestazioni: se il Content-Type non è text/html, o c'è un Content-Disposition: attachment, l'host sta già servendo il file (tipico degli account premium, confermato su terabytez e filestore) e il corpo non viene letto. In quel caso Resolve restituisce come URL il link originale: il downloader rifarà la GET con gli stessi cookie e seguirà gli stessi redirect.

Se la risposta è HTML, Resolve cerca un link diretto nella pagina; se non c'è, esegue fino a tre passi del form di download XFileSharing (op=download1 → op=download2): a ogni passo verifica il countdown, prende il primo <form> che contiene un campo name="op" (extractDownloadForm), lo invia con tutti i suoi <input> e cerca di nuovo il link. Alla fine, se la pagina contiene la parola «premium», l'errore suggerisce un file solo-premium.

Nome del file

Non tutti gli host mettono il nome nell'URL: terabytez sì (/id/nome.rar), filestore no (solo un id opaco). L'ordine delle fonti:

CasoFonti, in ordine
File servito direttamenteContent-Disposition della risposta → path dell'URL finale (dopo i redirect) → path del link originale.
Pagina HTMLresolvedName: campo nascosto fname → <title>, <h1-4>, <font> se contengono un nome con estensione → path del link diretto → path del link originale.
Nessuna fonteName vuoto: main usa fileNameFromURL (l'id opaco) e il downloader lo sostituisce con il Content-Disposition della sonda se il nome non ha estensione.

nameFromURLPath accetta un segmento solo se ha un'estensione, così un id opaco viene scartato. cleanFileName decodifica le entità HTML, toglie componenti di percorso (anche con \) e punti o spazi ai bordi: un nome come ../../etc/passwd diventa passwd. cdFileName (download.go:458) usa mime.ParseMediaType, preferisce filename* (RFC 5987) e ha un ripiego con espressione regolare per le intestazioni malformate.

Euristiche HTML

extractDirectLink (resolver.go:405) prova queste espressioni in ordine; vince la prima che trova un link che non sia un asset (.css, .js, /themes/, /images/):

#Cerca
1href verso un percorso /d/ID/nome (schema tipico dei server di download XFileSharing).
2Un <a> subito dentro un elemento con id direct_link / direct-link.
3, 4Un <a> con classe download, con href prima o dopo la classe.
5Qualunque href che finisce con un'estensione di file comune (iso zip rar 7z mkv mp4 avi tar gz tgz bin img exe pdf epub deb rpm).

detectCountdown considera countdown la presenza di id="countdown", countdown_str, please wait, seconds to download o wait_time.

Con --debug DIR, dump salva le pagine di ogni passo:

Adattare il resolver a un sito nuovo

  1. Aggiungi account e un link, poi make && ./hoster --dry-run --debug dbg.
  2. Login: in login_*_2result.html c'è l'area utente? Se no, guarda il form in login_*_1page.html: nomi dei campi diversi da login/password, un token con altro nome, un captcha (allora il sito non è supportabile). Adegua ensureLogin o looksLoggedIn.
  3. Link diretto: in file_*_N.html cerca dove sta il link al file e aggiungi un'espressione a directLinkREs, nella posizione giusta per la precedenza.
  4. Nome: se il nome esce sbagliato, guarda pageNameREs e fname.
  5. Aggiungi un test in resolver_test.go con un estratto (anonimizzato) della pagina vera, poi make test. Aggiorna l'elenco in help.go (supportedHosts, hostsTested) e le tabelle dei siti nei manuali.

Il motore di download

Sonda, flusso singolo e segmentato, ripresa, tentativi e link scaduti.

Il client

newDownloadClient (download.go:63) condivide il jar del resolver e usa il ripiego TLS. Non ha un timeout totale: un download di molti gigabyte non deve scadere. I timeout di --timeout valgono per la connessione (net.Dialer), l'handshake TLS e l'attesa delle intestazioni di risposta. MaxIdleConnsPerHost è -s + -j.

La sonda

probe (download.go:105) fa una GET con Range: bytes=0-0:

RispostaSignificato
206Range supportati; dimensione dal totale di Content-Range.
200Range ignorati; dimensione da Content-Length (o −1).
416File vuoto.
altrohttpError con il codice.

Legge e scarta al massimo 64 KB del corpo, così la connessione torna riutilizzabile. Raccoglie anche il nome dal Content-Disposition.

downloadFile

downloadFile (download.go:145) coordina un file:

  1. Se la destinazione esiste e -c non è attivo, esce subito con successo (file già scaricato).
  2. Sonda. Se il nome corrente non ha estensione e il server dichiara un nome, la destinazione diventa quel nome.
  3. Sceglie segmented se il server accetta i range, il file è di almeno 1 MB (MinSplit) e -s > 1; altrimenti singleStream. Scrive sempre su DEST.part e rinomina solo a successo.
  4. Se sonda o download falliscono per un link scaduto, chiama refresh (al massimo maxRefresh = 2 volte), toglie la barra senza contarla come fallimento (cancelFile) e ricomincia dal punto 2.

isStaleLink considera scaduto un httpError 401, 403, 404 o 410.

Flusso singolo

singleStream (download.go:349) è il caso normale (1 connessione per file):

  • Punto di partenza: con -c e range supportati riparte dalla dimensione del .part esistente (se minore del totale); altrimenti tronca a zero.
  • A ogni tentativo riparte dall'offset realmente scritto (fp.done), con Range: bytes=N-. Se il server ignora il range e risponde 200, riscrive dall'inizio. Senza range supportati tronca e ricomincia.
  • Scrittura posizionale con WriteAt: niente accodamento, quindi niente byte duplicati. Il test TestDownloadFileResumesAfterMidStreamDrop protegge proprio questo: la vecchia versione accodava e produceva file più grandi e corrotti.
  • Controllo di fine: se la dimensione è nota e lo stream finisce prima, l'errore download incompleto: X/Y byte fa scattare un nuovo tentativo.

Download segmentato

segmented (download.go:228) divide il file in -s segmenti uguali (makeSegs; l'ultimo prende il resto), prealloca il .part con Truncate e lancia un goroutine per segmento, ognuno con i propri tentativi e Range: bytes=da-a. Ogni 1,5 secondi, e in caso di errore, salva lo stato nel file accanto:

{"url":"https://…","size":1288490188,"done":[322122547,310000000,322122547,300000000]}

Con -c lo stato viene ricaricato solo se dimensione e numero di segmenti coincidono. A successo il file di stato viene cancellato e il .part rinominato.

Tentativi

withRetry (download.go:440) esegue la funzione fino a 1 + --retries volte, attendendo --retry-wait secondi tra un tentativo e l'altro. Un errore da link scaduto interrompe subito i tentativi: insistere sullo stesso URL è inutile, ci pensa downloadFile a rigenerarlo.

Limite di banda

RateLimiter (util.go:122) è un token bucket globale, condiviso da tutti i download, con capacità pari a un secondo di banda. meterReader avvolge ogni corpo di risposta e chiama Take(n) dopo ogni lettura, dormendo se i token sono finiti. parseSize accetta un numero (anche decimale) con suffisso k/M/G/T in potenze di 1024.

Il ripiego TLS

Come hoster tollera le catene di certificati incomplete senza rinunciare alla verifica altrove.

Alcuni server di download (confermato su fsNN.terabytez.org:183, certificato GlobalSign) inviano solo il certificato foglia, senza l'intermedio. I browser completano la catena da soli; crypto/tls di Go no e fallisce con x509: certificate signed by unknown authority.

tlsFallbackTransport (tls.go:19) tiene due trasporti clonati dallo stesso base, uno con verifica e uno con InsecureSkipVerify:

  1. Con -k usa sempre quello senza verifica.
  2. Se l'host (req.URL.Host, porta compresa) è già noto come «catena incompleta», usa quello senza verifica.
  3. Altrimenti prova con verifica. Solo se l'errore è un x509.UnknownAuthorityError (isIncompleteChain) memorizza l'host, stampa la nota (una volta sola) e ripete la richiesta con un clone senza verifica.

Scadenza, hostname errato e ogni altro errore restano errori. Resolver e downloader hanno ciascuno il proprio trasporto, quindi la nota può comparire una volta per ciascuno.

Barre di avanzamento

Come vengono disegnate le barre senza rovinarle con i messaggi.

Progress (progress.go:40) tiene l'elenco dei file in corso. Se stderr è un terminale e l'uscita non è silenziata, run ridisegna ogni 120 ms l'area viva: una riga per file più il piede «N in corso · M completati · K falliti». Per ridisegnare risale di liveLines-1 righe (ESC[nA), cancella fino in fondo (ESC[J) e riscrive.

I messaggi passano da Log (o notef, progress.go:18, che usa il gProg globale se c'è): cancellano l'area viva, stampano il messaggio e ridisegnano, così il messaggio resta sopra le barre. Senza terminale, i messaggi sono righe semplici e le barre non ci sono.

La velocità è una media mobile esponenziale (0,6 × precedente + 0,4 × istantanea), aggiornata al massimo ogni 100 ms. La barra usa gli ottavi di blocco Unicode (▏▎▍▌▋▊▉) per la frazione. La larghezza è colonne − 74, tra 8 e 28 celle; il nome è troncato o riempito a 28 caratteri.

Con -qe o -qa Progress è quiet: niente barre e nessuna riga di log, compresi gli errori dei singoli file. La differenza tra i due è solo la riga scaricati/falliti in main. NO_COLOR disattiva i colori.

Estrazione

Trovare i set di archivi, provare le password, estrarre in sicurezza.

Trovare i set

findArchiveSets (extract.go:214) scorre la cartella (non le sottocartelle) e tiene: ogni .zip; ogni .rar tranne le parti .partN.rar con N diverso da 1 (rePart, zeri iniziali ammessi). Per il set Kali (15 parti più i .rev) resta solo part01.rar (TestKaliMultiVolumeSet). I volumi vecchio stile .r00, .r01 non sono .rar, quindi resta il solo .rar principale, e rardecode trova da sé i volumi successivi.

Password e ordine dei tentativi

buildPasswords costruisce la lista senza duplicati: "", poi -p, poi le righe di --pwfile (vuote e # escluse; file assente ignorato). extractSet (extract.go:194) prova tutte le password con il decoder interno e, solo se falliscono tutte, tutte le password con il primo strumento esterno trovato tra rar, unrar, 7z, 7za, 7zz. Il metodo usato finisce nel messaggio (integrato o esterno (TOOL)).

  • RAR (goExtractRAR): rardecode.OpenReader con l'opzione password; gestisce multi-volume e cifratura.
  • ZIP (goExtractZIP): archive/zip. Gli ZIP cifrati (bit 0 dei flag) vengono rifiutati e passano allo strumento esterno.
  • Esterni: rar/unrar x -y -o+ -pPW (-p- senza password); 7z x -y -pPW -oDEST. L'uscita dello strumento si vede solo per i tentativi con password.

Sicurezza dei percorsi

safeJoin (extract.go:49) normalizza il nome (\ → /, Clean("/"+nome)) e verifica che il risultato stia dentro la cartella di destinazione: un ../../x nell'archivio produce l'errore percorso non sicuro (zip-slip). Vale sia per RAR sia per ZIP.

Pulizia

removeSet ricava la base del set (archiveBase: toglie .partN.rar, .rar o .zip) e cancella nella cartella i file che corrispondono a BASE.(partN.rar|partN.rev|rar|rNN|rev|zip), senza distinzione tra maiuscole e minuscole.

Guida e interfaccia

Una sola fonte per il testo della guida, tre modi di mostrarla.

Il contenuto della guida sta in help.go: helpSections (le opzioni per sezione), supportedHosts, hostsTested, helpExamples, descrizione. Da lì nascono sia la pagina di manuale (buildHelp, con colori ANSI) sia le schede della TUI (buildTabs). TestHelpCoversAllFlags confronta le opzioni definite con flag con quelle della guida: nessuna mancante, nessuna fantasma.

wantsHelp intercetta -h, -help, --help e help prima di flag.Parse. displayHelp sceglie:

  1. stdin o stdout non sono terminali → testo semplice senza colori su stdout;
  2. altrimenti la TUI (runTUI); se fallisce (terminale sotto 44×10, o sistema diverso da Linux) →
  3. pagina a colori nel pager: $PAGER, oppure less -R -F -X, oppure more, oppure stampata così com'è.

La TUI (tui.go) usa lo schermo alternativo (ESC[?1049h), nasconde il cursore e mette stdin in raw mode con ioctl TCGETS/TCSETS (term_linux.go). Un goroutine legge i byte e parseKeys li traduce in eventi (frecce, ESC[5~/ESC[6~, tasti vi); un ESC isolato vale come uscita. SIGWINCH ridisegna alla nuova dimensione; SIGTERM/SIGHUP escono ripristinando il terminale. Le parti di terminale vengono da scrap, il progetto gemello.

Il test dal vivo

TestLiveResolve (live_test.go) risolve, senza scaricare, i link reali di LISTA_LINKS con l'account reale, senza -k (verifica così anche il ripiego TLS). Parte solo con HOSTER_LIVE=1 (make live); HOSTER_ACCOUNT e HOSTER_LINKS cambiano i file. Fallisce se nessun link si risolve o se un nome esce vuoto.

Controlli della documentazione

tools/check-docs.py, eseguito da make test e quindi dalla CI, fallisce se:

  • un'opzione di helpSections non ha la sua voce nel riferimento del manuale utente (data-index di un <dt>), o il manuale documenta un'opzione che non esiste;
  • un file .go manca dalla mappa dei file, o il numero di righe indicato si scosta di più del 10% da quello vero;
  • l'eseguibile ./hoster manca, non è un ELF x86-64 o non contiene la versione di help.go (segno che non è stato rigenerato dopo un cambio di versione);
  • la versione di help.go non coincide con quella di README.md, docs/index.html e dei due manuali;
  • un link interno #ancora dei manuali punta a un id che non esiste.

Convenzioni

Come si scrive codice e testo in questo progetto.

  • Tutto in italiano: messaggi, commenti, documentazione. I testi rivolti all'utente sono semplici, senza gergo tecnico.
  • Formato: gofmt; go vet pulito.
  • Nessuna nuova dipendenza senza una ragione forte: il binario unico è una scelta di progetto.
  • Ogni correzione nata sul campo ha il suo test di regressione, con un server fittizio.
  • La documentazione si aggiorna insieme al codice: nuova opzione → riga in helpSections e voce nel riferimento del manuale utente; nuovo file → riga nella mappa.
  • Mai dati personali nel repository: niente credenziali, link personali o dump di debug, nemmeno nei test (usare example.test).

Limiti noti e punti aperti

Comportamenti noti da correggere, e idee per il futuro.

Limiti noti

DoveComportamentoEffetto
download.go:146Con -c il controllo «il file esiste già» viene saltato del tutto. Un file già completo viene riscaricato da zero (il .part non esiste).
download.go:146, main.go:170Il controllo di esistenza e quello dei duplicati usano il nome noto prima della sonda. Quando il nome vero arriva solo dal Content-Disposition della sonda (nessuna altra fonte), un file già scaricato non viene riconosciuto e due link allo stesso file non vengono deduplicati.
main.goLo stato di uscita è 0 anche con download o risoluzioni fallite. Uno script non può accorgersi dei fallimenti se non leggendo la riga finale.
resolver.go:142Il mutex protegge solo la mappa loggedIn, non il login. Due ri-risoluzioni simultanee sullo stesso host possono fare il login due volte (innocuo, ma ridondante).
resolver.go:187looksLoggedIn è permissiva. Un login fallito può essere preso per riuscito; l'errore emerge dopo.
progress.go:141In modalità quiet anche gli errori dei singoli file sono soppressi. -qe non mostra «solo errori» come dice la guida, ma solo errori fatali e il conteggio.
extract.go:166La password passa agli strumenti esterni come argomento. È visibile nell'elenco dei processi (ps) durante l'estrazione esterna.
extract.go:194Un tentativo fallito non ripulisce i file già scritti. Dopo una password errata possono restare file parziali, poi sovrascritti dal tentativo giusto.
main.goIl lotto successivo parte solo quando tutto il lotto corrente è finito. Un file lento o bloccato lascia inattivi gli altri posti.
main.go--dry-run crea comunque la cartella di destinazione. Compare una downloads/ vuota.

Idee per il futuro

  • Verificare gli altri siti dell'elenco e promuoverli a «provati».
  • Riparazione automatica con i .rev quando una parte è danneggiata (serve rar).
  • Limiti di parallelismo per sito (alcuni siti limitano i download contemporanei).
  • Stato in JSON per script e integrazioni.
  • Coda persistente su disco, per riprendere un'intera sessione dopo una chiusura.
  • Binari anche per macOS e Windows.

Glossario

XFileSharing Pro
Script commerciale per siti di file hosting; molti siti lo usano, con le stesse pagine e gli stessi campi (op=login, op=download1…).
Link diretto
L'URL che restituisce il file, di solito su un server di download diverso dal sito e a scadenza breve.
Id opaco
Un codice senza significato al posto del nome del file nell'URL (/nhail4vmw015).
Content-Disposition
Intestazione HTTP con cui il server indica il nome del file da salvare.
Richiesta Range
Richiesta HTTP di una parte del file (bytes=da-a); risposta 206 se supportata.
Catena di certificati
Foglia → intermedi → radice fidata. Se il server non invia gli intermedi, la catena è incompleta.
Zip-slip
Archivio con nomi come ../../file, costruito per scrivere fuori dalla cartella di estrazione.
Git bundle
Un file che contiene un repository git completo, clonabile senza rete.
