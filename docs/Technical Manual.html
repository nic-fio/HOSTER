    Chapter 1

    Introduction and concepts

    1.1 · What hoster is

    hoster is a terminal-based multi-host download manager, in the style of JDownloader but without Java: a single static executable that reads an accounts file and a list of links, signs in once per site, works out the direct link of each file (sites of the XFileSharing family), downloads several files at once with resume and, on request, extracts the RAR/ZIP archives.

    The user manual explains what hoster does; this one explains how. After reading it you should know where to work in order to adapt the resolver to a new site, change the download engine or the extraction without breaking the rest, and verify your changes. It assumes you know Go and the basics of HTTP. The why of the choices is in decisions and history (in Italian).

    i
    Code references. References of the form file.go:riga (riga = line) point to version 1.0. Functions are always cited by name, so they can still be found even if the lines move.

    1.2 · Principles

    Six principles guide all the choices in the code. They are decisions that have been made and documented, not to be reopened without a strong reason (the complete list is in CLAUDE.md).

    A single binary
    Static executable (CGO_ENABLED=0), no mandatory external program. Only library: rardecode. The download and extraction engines are built in.
    One resolver for all
    XFileSharing sites share the same server-side script: a generic logic with heuristics covers almost all of them.
    Premium only
    No bypassing of captchas or countdowns: if the countdown appears, the error says so. An ethical choice and one of robustness.
    Robust in the field
    Resume without duplication, size check, expired links regenerated, TLS tolerant only where needed.
    Tests without a network
    47 hermetic tests with fake HTTP servers; the live test runs only if requested.
    Documentation is code
    make test fails if an option or a file is not documented or if the version does not match.

    Other decisions that affect the code: no scrap subprocess (the engine of the sister project was re-implemented here, scrap remains untouched, the option names are harmonized); one bar per file (premium accounts give one connection per file, so the multi-segment view is not needed); TLS with automatic, targeted fallback (Ch. 6).

    1.3 · Subsystems at a glance

    The program is organized into cohesive subsystems, one or two files each. This is the map that the manual explores in depth chapter by chapter:

    main.go
    Startup, options, special modes and batch loop (Ch. 3).
    accounts.go, links.go
    The two input files and the site ↔ account matching (Ch. 4).
    resolver.go
    XFileSharing login and transformation of a file page into a direct link with the real name (Ch. 5).
    tls.go
    Fallback without verification only for incomplete certificate chains (Ch. 6).
    download.go, util.go
    Download engine: probe, single or segmented stream, resume, attempts, bandwidth (Ch. 7).
    progress.go, help.go, tui.go, term_*.go
    Progress bars, built-in guide and TUI (Ch. 8).
    extract.go
    RAR/ZIP extraction with passwords and fallback to external tools (Ch. 9).
    *_test.go, tools/, Makefile, CI
    Tests, documentation checks, build and release (Ch. 10 and Ch. 11).

    1.4 · File map

    The whole program is a single package main. The line counts are checked by tools/check-docs.py: if a file changes length by more than 10% (with a minimum of 3 lines), or a new one appears without a row here, make test fails (§ 10.4).

    Chapter 2

    Overall architecture

    2.1 · Components

    hoster is a short-lived command-line program: it starts, works through the list of links and exits. It has no persistent state beyond the files it writes (.part, .part.hoster, the downloaded files).

    The key point is the shared cookie jar: the resolver signs in and obtains the session cookies; the download client (newDownloadClient, download.go:63) receives the same jar (res.jar), so it downloads with the same session. The User-Agent (-U) is also the same for both, because some sites tie the session to the UA (TestResolverUsesConfiguredUserAgent guards this).

    Resolver and downloader, on the other hand, have separate clients and transports: the resolver has an overall timeout of 90 s, the downloader no overall timeout but timeouts on connection, handshake and headers. Each one wraps its own transport in a tlsFallbackTransport (Ch. 6).

    2.2 · A run

    The loop in main.go proceeds in batches of -j links: it resolves all the links in the batch in sequence, starts one goroutine per file and waits for the whole batch to finish (sync.WaitGroup) before moving on to the next. This way the direct links are generated shortly before use, because they expire quickly. The flip side of the coin: a slow file holds up the next batch (Ch. 13).

    for bi := 0; bi < len(links); bi += *jobs {
	end := min(bi+*jobs, len(links))
	chunk := links[bi:end]

	// Risolvo il lotto (i link diretti scadono: meglio "freschi" appena prima).
	var direct []Resolved
	for _, link := range chunk {
		r, err := res.Resolve(link)
		...
	}
	// Scarico il lotto in parallelo.
	var wg sync.WaitGroup
	...
	wg.Wait()
}

    Before starting a download, main computes the destination (Name, or fileNameFromURL if empty) and records it in seenDest: a second link to the same file is skipped as a duplicate (main.go:170). The refresh function passed to the downloader calls Resolve again on the original link (Resolved.Link) when the direct link expires.

    fileNameFromURL takes the last segment of the path, decoded; if the URL cannot be parsed or the segment is empty, / or . it returns download.bin.

    2.4 · Where the output goes

    Bars, log lines and the download summary go to stderr; the line scaricati: N falliti: M (downloaded, failed), the output of --dry-run and that of the extraction go to stdout. Fatal errors (fatal, main.go:227) go to stderr with the prefix hoster: and status 1. The flag package exits with status 2 on unknown options, printing the guide as plain text on stderr (flag.Usage = usage).

    Chapter 3

    Startup and configuration

    3.1 · The startup sequence

    All configuration comes from the command line: hoster reads no settings files and no environment variables, apart from NO_COLOR, PAGER, the proxy variables (http.ProxyFromEnvironment) and those of the tests (HOSTER_LIVE, HOSTER_ACCOUNT, HOSTER_LINKS).

    1. wantsHelp intercepts -h, -help, --help and help before flag.Parse (up to a possible --): displayHelp, then exit with status 0.
    2. flag.Parse reads the options. Go's flag package accepts every option with either one dash or two (-dry-run and --dry-run are the same thing).
    3. With --extract-only DIR it runs runExtraction and ends: neither accounts nor links are needed.
    4. parseSize interprets --rate; LoadAccounts and LoadLinks read the two files. An error here, or an empty list, is fatal.
    5. It creates the destination folder (MkdirAll, even in --dry-run) and the Resolver.
    6. With --dry-run it resolves every link, prints name and direct link and ends.
    7. Otherwise it creates Progress (and publishes it in gProg), the download client and the Downloader, runs the batch loop, prints the summary and, with -e, extracts.

    3.2 · The options and where they act

    The table follows the options from the point where they are defined (main.go) to the code that uses them. The reference for the user, with examples, is in the option reference of the user manual.

    i
    Note. The 23 rows of the guide (helpSections) are the source for the documentation: TestHelpCoversAllFlags checks their number and tools/check-docs.py checks that each one has its entry in the user manual.

    3.3 · From the options to the engine: DLConfig

    The download options converge in DLConfig, passed to NewDownloader together with the client and the Progress:

    dlClient := newDownloadClient(res.jar, *timeout, *split+*jobs, insecure)
dl := NewDownloader(dlClient, DLConfig{
	Split:     *split,
	Jobs:      *jobs,
	MinSplit:  1 << 20,
	Continue:  *cont,
	Retries:   *retries,
	RetryWait: *retryWait,
	Rate:      rate,
	Timeout:   *timeout,
	UserAgent: *ua,
}, prog)

    MinSplit is not an option: it is fixed at 1 MiB, below which a file is never segmented. The fields Jobs and Timeout are stored but the Downloader does not read them: connection pool and timeouts are already applied by newDownloadClient (Appendix A).

    3.4 · Special modes

    --dry-run uses the same Resolver as the download (login, TLS, debug dump), but does not create either Progress or Downloader: for each link it prints ✓ nome and the direct link, or ✗ link and the error; at the end risolti: N falliti: M. It is the main tool for trying a new site (Ch. 12).

    --extract-only DIR is checked right after flag.Parse, even before reading --rate: it extracts and ends (Ch. 9).

    -v adds after each resolution the line → nome link-diretto, useful for seeing which link was chosen without running a --dry-run.

    3.5 · Exit statuses

    !
    Warning. The built-in guide describes status 1 as «errore durante l'esecuzione» (error during execution), but failed downloads do not produce it: a script must read the line scaricati: N falliti: M. This is a known limitation (§ 13.1).
    Chapter 4

    Accounts and links

    4.1 · Format of account

    LoadAccounts (accounts.go:45) reads one line at a time, after TrimSpace, and skips blank lines and # comments. firstSep finds the first of : and ;: the first separator closes the domain, the second the username, and the password is everything else, untrimmed (it may contain separators and internal spaces). The domain goes through normHost, the username through TrimSpace.

    If two lines have the same host or the same label, the last one wins: the maps are simply overwritten.

    4.2 · Matching host ↔ account

    Each account is indexed twice: by normalized host (byHost) and by label, the part before the first dot (byLabel). Lookup tries the exact host first, then the label: this way terabytez:… applies to terabytez.org and terabytez.com.

    normHost (util.go:17) also accepts a whole URL: it lowercases, and strips scheme, path, query, fragment, credentials, port and www.. Note: labelOf takes the first label, so a subdomain such as fs12.terabytez.org gives fs12. This is not a problem because the lookup is done on the host of the file-page link, not on that of the download servers.

    func (a *Accounts) Lookup(host string) (Account, bool) {
	if acc, ok := a.byHost[normHost(host)]; ok {
		return acc, true
	}
	if acc, ok := a.byLabel[labelOf(host)]; ok {
		return acc, true
	}
	return Account{}, false
}

    4.3 · Format of links

    LoadLinks (links.go:11) skips blank lines and comments, trims surrounding spaces and deduplicates while keeping the order. The scanner buffer is 1 MB per line. There is no validation: an invalid URL is reported by Resolve (URL non valido, invalid URL) and counts as failed.

    Deduplication is on the text of the line: two different links that lead to the same file are stopped later, by seenDest, only if they produce the same destination name (§ 2.2).

    Chapter 5

    The resolver

    5.1 · The resolver's client

    The resolver is the heart of hoster: it performs the XFileSharing login and turns a file page into a direct link, with the real name of the file.

    NewResolver (resolver.go:33) creates a cookie jar and an http.Client with an overall timeout of 90 seconds (fixed, independent of --timeout) and the newTLSFallbackTransport transport (proxy from the environment, HTTP/2 attempted). do sets User-Agent and Accept and reads at most 16 MB of body; openFilePage reads at most 8 MB. The client follows redirects (Go's default behavior) and the jar collects the cookies of each step.

    5.2 · Login

    ensureLogin (resolver.go:142) performs the login only once per host: the loggedIn map is protected by mu, because the re-resolutions of expired links happen in parallel. The host is always contacted over https. If the login page has a hidden token field (CSRF), it is sent. Without an account for the host the error is nessun account nel file 'account' per HOST (no account in the 'account' file for HOST).

    form := url.Values{}
form.Set("op", "login")
form.Set("login", acc.User)
form.Set("password", acc.Pass)
form.Set("redirect", base+"/")
if tok := extractHidden(page, "token"); tok != "" {
	form.Set("token", tok)
}
res, _, err := r.postForm(base+"/", form, base+"/?op=login")

    looksLoggedIn (resolver.go:187) is a heuristic:

    1. if the page contains incorrect login, wrong password or username and password do not match → failed;
    2. if it contains op=logout, logout, my account or myaccount → succeeded;
    3. otherwise succeeded if the jar contains an xfss, xfsts or login cookie, or one with sess in its name.
    !
    Limitation. The heuristic is permissive: the word «logout» anywhere in the page, or an anonymous session cookie, is enough to declare the login successful. A login that has actually failed shows up later, as «countdown rilevato» (countdown detected) or «link diretto non trovato» (direct link not found).

    5.3 · Resolution

    openFilePage (resolver.go:103) opens the file page and decides from the headers only: if the Content-Type is not text/html, or there is a Content-Disposition: attachment, the host is already serving the file (typical of premium accounts, confirmed on terabytez and filestore) and the body is not read. In that case Resolve returns as the URL the original link: the downloader will repeat the GET with the same cookies and follow the same redirects.

    If the response is HTML, Resolve looks for a direct link in the page; if there is none, it performs up to three steps of the XFileSharing download form (op=download1 → op=download2): at each step it checks for the countdown, takes the first <form> that contains a name="op" field (extractDownloadForm), submits it with all its <input> elements (action made absolute with resolveURL; without an action, the page itself) and looks for the link again. At the end, if the page contains the word «premium», the error suggests a premium-only file.

    5.4 · File name

    Not all hosts put the name in the URL: terabytez does (/id/nome.rar), filestore does not (only an opaque id). The order of the sources:

    nameFromURLPath accepts a segment only if it has an extension, so an opaque id is discarded. cleanFileName decodes HTML entities, removes path components (including those with \) and leading or trailing dots and spaces: a name like ../../etc/passwd becomes passwd. cdFileName (download.go:458) uses mime.ParseMediaType, prefers filename* (RFC 5987) and has a regular-expression fallback for malformed headers.

    5.5 · HTML heuristics

    extractDirectLink (resolver.go:405) tries these expressions in order; the first one that finds a link that is not an asset (.css, .js, /themes/, /images/) wins. The link found is decoded from HTML entities.

    detectCountdown treats as a countdown the presence of id="countdown", countdown_str, please wait, seconds to download or wait_time. The helper functions are in util.go: attr extracts an attribute with double or single quotes and decodes its entities; extractHidden looks up the value of an <input> by name.

    5.6 · Debug dump

    With --debug DIR, dump saves the pages of each step (creating the folder):

    LINK is the link reduced by safeName to alphanumeric characters and _, at most the last 60.

    !
    Confidentiality. The dumps contain pages seen as a signed-in user. The dbg/ folder is in .gitignore: it must never be committed.
    Chapter 6

    The TLS fallback

    6.1 · The problem: incomplete chains

    hoster tolerates incomplete certificate chains without giving up verification elsewhere.

    Some download servers (confirmed on fsNN.terabytez.org:183, GlobalSign certificate) send only the leaf certificate, without the intermediate one. Browsers complete the chain on their own; Go's crypto/tls does not and fails with x509: certificate signed by unknown authority. Login and resolution succeed; only the handshake with the node that serves the file fails.

    6.2 · tlsFallbackTransport

    tlsFallbackTransport (tls.go:19) holds two transports cloned from the same base, one with verification and one with InsecureSkipVerify:

    1. With -k it always uses the one without verification.
    2. If the host (req.URL.Host, port included) is already known as an «incomplete chain», it uses the one without verification.
    3. Otherwise it tries with verification. Only if the error is an x509.UnknownAuthorityError (isIncompleteChain, with errors.As) does it remember the host, print the note (only once) and repeat the request with a clone without verification.
    func (t *tlsFallbackTransport) RoundTrip(req *http.Request) (*http.Response, error) {
	if t.force {
		return t.insecure.RoundTrip(req)
	}
	if _, known := t.bad.Load(req.URL.Host); known {
		return t.insecure.RoundTrip(req)
	}
	resp, err := t.secure.RoundTrip(req)
	if err != nil && isIncompleteChain(err) {
		if _, seen := t.bad.LoadOrStore(req.URL.Host, struct{}{}); !seen {
			notef("nota: %s ha una catena di certificati incompleta — verifica TLS saltata per questo host", req.URL.Host)
		}
		return t.insecure.RoundTrip(req.Clone(req.Context()))
	}
	return resp, err
}

    6.3 · What is still rejected

    Expiry, wrong hostname and every other error remain errors: the exception applies only to «unknown authority» and only to that host. Resolver and downloader each have their own transport, so the note may appear once for each. The memory of the hosts is per run: it is not saved to disk.

    i
    Verified in the field. The complete Kali set (15 volumes, about 18 GB) was downloaded from terabytez without -k, with only the automatic fallback. TestLiveResolve deliberately uses force=false.
    Chapter 7

    The download engine

    7.1 · The client

    The download engine is the re-implementation, inside hoster, of that of scrap: probe, single or segmented stream, resume, attempts and expired links.

    newDownloadClient (download.go:63) shares the resolver's jar and uses the TLS fallback. It has no overall timeout: a download of many gigabytes must not time out. The --timeout timeouts apply to the connection (net.Dialer), the TLS handshake and the wait for the response headers. MaxIdleConns is 100, MaxIdleConnsPerHost is -s + -j.

    base := &http.Transport{
	Proxy:                 http.ProxyFromEnvironment,
	DialContext:           (&net.Dialer{Timeout: time.Duration(timeout) * time.Second}).DialContext,
	TLSHandshakeTimeout:   time.Duration(timeout) * time.Second,
	ResponseHeaderTimeout: time.Duration(timeout) * time.Second,
	ForceAttemptHTTP2:     true,
	MaxIdleConns:          100,
	MaxIdleConnsPerHost:   maxConns,
}
return &http.Client{Transport: newTLSFallbackTransport(base, forceInsecure), Jar: jar}

    7.2 · The probe

    probe (download.go:105) performs a GET with Range: bytes=0-0:

    It reads and discards at most 64 KB of the body, so that the connection becomes reusable again. It also collects the Content-Type and the name from the Content-Disposition (probeInfo).

    7.3 · downloadFile

    downloadFile (download.go:145) coordinates one file:

    1. If the destination exists and -c is not active, it exits immediately with success (file already downloaded).
    2. Probe. If the current name has no extension and the server declares a name, the destination becomes that name.
    3. It chooses segmented if the server accepts ranges, the file is at least 1 MiB (MinSplit) and -s > 1; otherwise singleStream. It always writes to DEST.part and renames only on success.
    4. If the probe or the download fails because of an expired link, it calls refresh (at most maxRefresh = 2 times), removes the bar without counting it as a failure (cancelFile), prints nota: link diretto scaduto, lo rigenero (note: direct link expired, regenerating it) and starts again from step 2.
    func isStaleLink(err error) bool {
	var he *httpError
	if errors.As(err, &he) {
		switch he.code {
		case 401, 403, 404, 410:
			return true
		}
	}
	return false
}

    7.4 · Single stream

    singleStream (download.go:349) is the normal case (1 connection per file):

    • Starting point: with -c and ranges supported it resumes from the size of the existing .part (if smaller than the total, or if the total is unknown); otherwise it truncates to zero.
    • At each attempt it restarts from the offset actually written (fp.done), with Range: bytes=N-. If the server ignores the range and responds 200, it rewrites from the start. Without range support it truncates and starts over.
    • Positional writing with WriteAt: no appending, hence no duplicated bytes. The test TestDownloadFileResumesAfterMidStreamDrop guards exactly this: the old version appended and produced larger, corrupted files.
    • End check: if the size is known and the stream ends early, the error download incompleto: X/Y byte (incomplete download) triggers a new attempt.
    • HTTP statuses: a response ≥ 400 becomes an httpError; the read buffer is 64 KB and every read goes through the bandwidth limiter.

    7.5 · Segmented download

    segmented (download.go:228) splits the file into -s equal segments (makeSegs; the last one takes the remainder), preallocates the .part with Truncate and starts one goroutine per segment, each with its own attempts and Range: bytes=da-a (da-a = from-to) (fetchRange). Every 1.5 seconds, and in case of error, it saves the state in the file alongside:

    With -c the state is reloaded only if size and number of segments match (the saved URL is not compared). On success the state file is deleted and the .part renamed. In the single stream the .part.hoster file does not exist: resuming uses the size of the .part.

    7.6 · Attempts

    withRetry (download.go:440) runs the function up to 1 + --retries times, waiting --retry-wait seconds between one attempt and the next. An error from an expired link stops the attempts immediately: insisting on the same URL is pointless, downloadFile takes care of regenerating it.

    func (d *Downloader) withRetry(fn func() error) error {
	var err error
	for attempt := 0; attempt <= d.cfg.Retries; attempt++ {
		if attempt > 0 {
			time.Sleep(time.Duration(d.cfg.RetryWait) * time.Second)
		}
		if err = fn(); err == nil {
			return nil
		}
		if isStaleLink(err) {
			return err // inutile ritentare lo stesso URL scaduto: lo gestisce chi ri-risolve
		}
	}
	return err
}

    In the segmented download each segment has its own withRetry: one segment can retry while the others carry on.

    7.7 · Bandwidth limit

    RateLimiter (util.go:122) is a global token bucket, shared by all downloads, with a capacity equal to one second of bandwidth. meterReader wraps every response body and calls Take(n) after each read, sleeping if the tokens have run out. With --rate 0 (default) Take returns immediately.

    parseSize accepts a number (decimals too) with the suffix k/M/G/T (uppercase or lowercase) in powers of 1024; an empty string is 0; a non-numeric value gives dimensione non valida (invalid size), fatal at startup.

    Chapter 8

    Progress and terminal interface

    8.1 · Progress bars

    One bar per file, messages that scroll above the bars without spoiling them, and a tabbed built-in guide. All with ANSI sequences, without libraries.

    Progress (progress.go:40) keeps the list of files in progress. If stderr is a terminal and the output is not silenced, run redraws the live area every 120 ms: one line per file plus the footer «N in corso · M completati · K falliti» (in progress, completed, failed). To redraw it moves up liveLines-1 lines (ESC[nA), clears to the end (ESC[J) and rewrites.

    The speed is an exponential moving average (0.6 × previous + 0.4 × instantaneous), updated at most every 100 ms. The bar uses Unicode eighth blocks (▏▎▍▌▋▊▉) for the fraction. The width is colonne − 74 (columns − 74), between 8 and 28 cells; the name is truncated (with …) or padded to 28 characters. Without a known size the percentage becomes · and the remaining time is missing.

    8.2 · Messages above the bars

    Messages go through Log (or notef, progress.go:18, which uses the global gProg if there is one, otherwise writes to stderr): they clear the live area, print the message and redraw, so the message stays above the bars. Without a terminal, messages are plain lines and there are no bars. notef is for the components that do not know the Progress: the TLS fallback and the regeneration of links.

    8.3 · Quiet mode and colors

    With -qe or -qa Progress is quiet: no bars and no log lines, including the errors of individual files, and no final summary. The only difference between the two is the scaricati/falliti line in main. NO_COLOR (any non-empty value) turns off colors; without a terminal colors are off anyway.

    !
    Difference from the guide. The built-in guide says that -qe shows «solo gli errori» (only the errors), but the errors of individual files are suppressed: only fatal errors and the count remain (§ 13.1).

    8.4 · Built-in guide: one source, three views

    The content of the guide is in help.go: helpSections (the options by section), supportedHosts, hostsTested, helpExamples, descrizione. From there come both the manual page (buildHelp, with ANSI colors, width between 60 and 100 columns) and the TUI tabs (buildTabs: Info, one tab per option section, Host, Esempi). TestHelpCoversAllFlags compares the options with those of the guide: none missing, none phantom.

    wantsHelp intercepts -h, -help, --help and help before flag.Parse. displayHelp chooses:

    1. stdin or stdout are not terminals → plain text without colors on stdout;
    2. otherwise the TUI (runTUI); if it fails (terminal smaller than 44×10, or a system other than Linux) →
    3. colored page in the pager: $PAGER (run with sh -c), or less -R -F -X, or more, or printed as is.

    8.5 · The tabbed TUI

    The TUI (tui.go) uses the alternate screen (ESC[?1049h), hides the cursor and puts stdin into raw mode. A goroutine reads the bytes and parseKeys translates them into events; an isolated ESC counts as exit. SIGWINCH redraws at the new size; SIGTERM/SIGHUP exit restoring the terminal. The frame is drawn with box-drawing characters; the usable height is righe − 6 (rows − 6).

    8.6 · Terminal primitives

    term_linux.go (build constraint linux) provides termSize (ioctl TIOCGWINSZ on stdout, stderr, stdin and finally /dev/tty, with an 80×24 fallback), enterRaw and restoreTerm (ioctl TCGETS/TCSETS: turned off ECHO, ICANON, ISIG, IEXTEN, IXON, ICRNL…, VMIN=1) and the handled signals. term_other.go (!linux) defines the same symbols: enterRaw always fails, so the guide falls back to text. These parts come from scrap, the sister project.

    Chapter 9

    Extraction

    9.1 · Finding the sets

    Finding the archive sets, trying the passwords, extracting safely: all with the built-in decoder, with external tools only as a fallback.

    findArchiveSets (extract.go:214) scans the folder (not the subfolders) and keeps: every .zip; every .rar except the .partN.rar parts with N other than 1 (rePart, leading zeros allowed, case-insensitive). The result is sorted. For the Kali set (15 parts plus the .rev files) only part01.rar remains (TestKaliMultiVolumeSet). Old-style volumes .r00, .r01 are not .rar, so only the main .rar remains, and rardecode finds the following volumes by itself.

    Extraction takes place in the same folder as the archives (-d, or the folder given to --extract-only).

    9.2 · Passwords and order of attempts

    buildPasswords builds the list without duplicates: "", then -p, then the lines of --pwfile (blank lines and # excluded, trailing \r removed; missing file ignored). extractSet (extract.go:194) tries all the passwords with the internal decoder and, only if they all fail, all the passwords with the first external tool found among rar, unrar, 7z, 7za, 7zz. The method used ends up in the message (integrato, built-in, or esterno (TOOL), external), together with «nessuna password» (no password) or «password trovata» (password found); the password itself is not printed.

    9.3 · Internal decoder and external tools

    • RAR (goExtractRAR): rardecode.OpenReader with the password option; handles multi-volume archives and encryption. Folders created with 0755, files with 0644, overwritten if they exist.
    • ZIP (goExtractZIP): archive/zip. Encrypted ZIPs (bit 0 of the flags) are rejected and passed to the external tool. The choice between the two decoders is by extension (goExtract).
    • External (extractArgs, runExternal): rar/unrar x -y -o+ -pPW ARCHIVIO DEST/ (-p- without a password); 7z x -y -pPW -oDEST ARCHIVIO (ARCHIVIO = archive). The tool's output is visible only for the attempts with a password.

    9.4 · Path safety

    safeJoin (extract.go:49) normalizes the name (\ → /, Clean("/"+nome)) and checks that the result lies inside the destination folder. Thanks to the leading slash, a ../../x in the archive is brought back inside the folder; the final check produces the error percorso non sicuro (unsafe path) if the path still escaped (zip-slip). This applies to both RAR and ZIP; TestGoExtractZIPRoundTripAndSlip checks that nothing is written outside.

    func safeJoin(base, name string) (string, error) {
	name = strings.ReplaceAll(name, "\\", "/")
	clean := filepath.Clean("/" + name)
	target := filepath.Join(base, clean)
	root := filepath.Clean(base)
	if target != root && !strings.HasPrefix(target, root+string(os.PathSeparator)) {
		return "", fmt.Errorf("percorso non sicuro nell'archivio: %q", name)
	}
	return target, nil
}

    9.5 · Cleanup

    removeSet works out the base of the set (archiveBase: removes .partN.rar, .rar or .zip) and deletes the files in the folder that match BASE.(partN.rar|partN.rev|rar|rNN|rev|zip), case-insensitively. The other files (even with the same base, such as m.mkv) remain. It happens only after a successful extraction.

    Chapter 10

    Tests

    10.1 · The suite

    47 hermetic tests, no real network and no credentials, plus a live test that runs only on request.

    The servers are local httptest servers that imitate login, file pages, directly served files, connection drops half-way and links that expire. They run with -race because downloads, re-resolutions and bars are concurrent, and with -count=1 so as not to use cached results.

    10.2 · Fake servers

    Three tools make the tests without a network possible:

    rewriteRT (resolver_test.go)
    A RoundTripper that redirects every https://host/… request to the test server, keeping path, query and headers: this way cookies and session stay consistent even though the resolver believes it is talking to example.test.
    newFakeXFS
    A fake XFileSharing site: login page with a token, a POST that accepts only u/p/tok123, /file-direct which serves a binary with Content-Disposition, /file-html and /dl2 for the two-step path.
    serveData (download_test.go)
    A server based on http.ServeContent, hence with real ranges, and an optional Content-Disposition. The test of the mid-stream drop instead uses a hand-written handler that interrupts the first body with http.ErrAbortHandler.
    i
    Convention. The tests use only names such as example.test, h.test, cookie.test: never personal data, not even poorly anonymized.

    10.3 · The live test

    TestLiveResolve (live_test.go) resolves, without downloading, the real links in LISTA_LINKS with the real account, without -k (thus also verifying the TLS fallback). It runs only with HOSTER_LIVE=1 (make live); HOSTER_ACCOUNT and HOSTER_LINKS change the files. It fails if no link resolves or if a name comes out empty.

    !
    Who runs it. It must be run after every change to resolver, login or TLS, but it is the user who runs it: the credentials are theirs and do not leave their machine.

    10.4 · Documentation checks

    tools/check-docs.py, run by make test (and on its own with make docs-check), and therefore also by the CI, reads docs/User Manual.html and docs/Technical Manual.html and fails if:

    • an option in helpSections has no entry in the user manual's reference (a <dt data-kind="opzione" data-index="…"> between id="riferimento" and id="file-usati"), or the manual documents an option that does not exist;
    • a .go file is missing from the file map (the table with id="file-map"), the map cites a file that does not exist, or the number of lines given differs by more than 10% (minimum 3 lines) from the real one;
    • the executable ./hoster is missing, is not an x86-64 ELF or does not contain the version from help.go (a sign that it was not rebuilt after a version change);
    • the version in help.go ("hoster X.Y") does not match that of README.md, docs/index.html and the two manuals, where it must be written on the cover as <span>Version</span><b>X.Y</b>; in the Italian home page, docs/index.html, the word is Versione instead of Version;
    • an internal #anchor link in the manuals points to an id that does not exist, or a link from one manual to the other (User%20Manual.html#anchor) points to an anchor missing from the other.
    Chapter 11

    Build, CI and release

    11.1 · Repository structure

    !
    Personal files. account, links, LISTA_LINKS and passwords.txt are in .gitignore and must never enter the repository, which is public. Also ignored are dbg/ (the --debug dumps contain pages seen as a signed-in user), downloads/, build/, dist/, *.part, *.part.hoster and *.bundle. Never git add -A without looking.

    11.2 · Build

    $ tools/setup-dev.sh --install
$ make
$ make test
$ make dist

    On Debian 13 the golang-go package is already 1.24. With an older Go that is at least 1.21, the go 1.24 directive in go.mod automatically downloads the right toolchain. The first build downloads rardecode into the module cache. tools/setup-dev.sh checks for golang-go, build-essential (for gcc), make, python3 and git.

    11.3 · CI and releases

    The CI (.github/workflows/ci.yml) runs on every push to main, on every pull request, on every v* tag and on manual request: it installs Go at the version in go.mod, runs make test and make dist and keeps the binaries as an artifact. On a v* tag a second job creates the GitHub release with the two binaries and SHA256SUMS; the message of the annotated tag becomes the description, followed by fixed download instructions.

    For a release:

    1. Update the version in help.go ("hoster 1.0"), README.md, docs/index.html and on the cover of the two manuals. make test checks that they match.
    2. make and commit the new ./hoster (the check verifies that it contains the version).
    3. git tag -a v1.1.0 -m "hoster 1.1.0: …novità…"
    4. git push origin main v1.1.0

    11.4 · Recovery and backup

    The repository is designed so that a git clone is enough to get everything back, except the personal files. The ready-made program is already inside (./hoster); to rebuild and verify it:

    $ git clone https://github.com/nic-fio/HOSTER.git
$ cd HOSTER && tools/setup-dev.sh --install && make test

    tools/setup-dev.sh also sets the local git identity (nic-fio with the GitHub noreply address; HOSTER_GIT_NAME and HOSTER_GIT_EMAIL change it), which is not cloned because it lives in .git/config. tools/backup.sh DIR creates hoster-AAAA-MM-GG.bundle (AAAA-MM-GG = YYYY-MM-DD), verified with git bundle verify, and warns if there are uncommitted changes or commits not yet pushed to GitHub. With --personal it adds hoster-personali-AAAA-MM-GG.tar.gz (created with umask 077): it contains passwords in plain text and must be kept private. For the user, the procedure is described in the user manual.

    11.5 · The manuals

    The two manuals are self-contained HTML files: docs/User Manual.html and docs/Technical Manual.html. Style sheet, diagrams (SVG drawn in the document) and scripts are embedded: no external resources, no libraries. They open from the clone even without a network and print on A4 (cover on one page, one chapter per page, side contents hidden).

    • Search: the box in the sidebar (key /) filters the sections that contain all the words searched for, dims the contents entries that do not match, lists the results with an excerpt and, once a result is chosen (or with Enter), takes you to the section highlighting the occurrences. Esc clears it.
    • Index: generated on opening from the terms marked with the data-index attribute (several terms separated by ;), grouped by initial letter, each with a reference to its section.
    • Without JavaScript the manual remains complete and readable: the search box does not appear and the index shows a notice; the side contents and all the links work.

    The update rules are those of § 10.4: new option → row in helpSections and entry in the user manual's reference; new .go file → row in this manual's file map; new version → cover of both.

    11.6 · Conventions

    • Italian for the program, English for the manuals: messages, comments and the built-in guide are in Italian; the two manuals are in English. Texts addressed to the user are simple, without technical jargon («copy di prodotto», product copy).
    • Format: gofmt; clean go vet.
    • No new dependencies without a strong reason: the single binary is a design choice.
    • Every fix born in the field has its own regression test, with a fake server.
    • Verify, don't declare: every statement about behavior comes from a run (tests, --dry-run, real download).
    • Documentation is updated together with the code: a feature is not finished until the manuals describe it.
    • Never personal data in the repository: no credentials, personal links or debug dumps, not even in the tests (use example.test).
    • Commits with the local identity set by tools/setup-dev.sh; before committing: make test, make if the code has changed, git status without personal files.
    Chapter 12

    How to add a site

    12.1 · The work cycle

    A site of the XFileSharing family often works without touching the code: the line in account is enough. When it is not enough, the work is almost always in resolver.go.

    1. Add the account and a link, then make && ./hoster --dry-run --debug dbg.
    2. Login: does login_*_2result.html show the user area? If not, look at the form in login_*_1page.html: field names other than login/password, a token with a different name, a captcha (in which case the site cannot be supported). Adapt ensureLogin or looksLoggedIn.
    3. Direct link: in file_*_N.html look for where the link to the file is and add an expression to directLinkREs, in the right position for precedence.
    4. Name: if the name comes out wrong, look at pageNameREs and fname.
    5. Add a test in resolver_test.go with an (anonymized) excerpt of the real page, then make test. Update the list in help.go (supportedHosts, hostsTested) and the site tables in the manuals.

    12.2 · Where to intervene

    ✓
    Before committing. make test green, make and commit of ./hoster, and a make live run by the user with their real files: the resolver is one of the parts for which the live test is mandatory.

    Chapter 15

    Glossary

    15.1 · Terms A–L

    Definitions of the terms used in the manual. The references indicate the chapter that covers them in depth.

    Content-Disposition
    HTTP header with which the server indicates the name under which to save the file. See Ch. 5 and 7.
    Certificate chain
    Leaf → intermediates → trusted root. If the server does not send the intermediates, the chain is incomplete. See Ch. 6.
    Cookie jar
    The container of the session cookies, shared by resolver and downloader. See Ch. 2.
    Countdown
    The wait imposed on free users before the download. It does not appear with premium: if it is there, hoster stops. See Ch. 5.
    Git bundle
    A file that contains a complete git repository, which can be cloned without a network. See Ch. 11.
    ID (opaque)
    A meaningless code in place of the file name in the URL (/nhail4vmw015).
    Link (direct)
    The URL that returns the file, usually on a download server different from the site and with a short expiry.
    Batch
    Group of -j links resolved in sequence and then downloaded in parallel. See Ch. 2.

    15.2 · Terms M–Z

    Page (file page)
    The site's page that corresponds to a link in the list; with premium it often serves the file directly.
    .part / .part.hoster
    The partial file being written and, in the segmented download, the resume state in JSON. See Ch. 7.
    Range request
    HTTP request for a part of the file (bytes=da-a, from-to); response 206 if supported.
    Re-resolution
    A new call to Resolve on the original link when the direct link turns out to have expired (401, 403, 404, 410).
    Probe
    The Range: bytes=0-0 request with which the downloader discovers size, range support and name. See Ch. 7.
    TUI
    Tabbed interface drawn in the terminal in raw mode: the --help guide. See Ch. 8.
    XFileSharing Pro
    Commercial script for file hosting sites; many sites use it, with the same pages and the same fields (op=login, op=download1…).
    Zip-slip
    Archive with names such as ../../file, crafted to write outside the extraction folder. See Ch. 9.
