    Capitolo 1

    Introduzione e concetti

    1.1 · Che cos'è hoster

    hoster è un gestore di download multi-host da terminale, in stile JDownloader ma senza Java: un unico eseguibile statico che legge un file di account e una lista di link, fa il login una volta per sito, ricava il link diretto di ogni file (siti della famiglia XFileSharing), scarica più file insieme con ripresa e, a richiesta, estrae gli archivi RAR/ZIP.

    Il manuale utente spiega cosa fa hoster; questo spiega come. Dopo averlo letto dovresti sapere dove mettere le mani per adattare il resolver a un sito nuovo, cambiare il motore di download o l'estrazione senza rompere il resto, e verificare le modifiche. Si dà per scontato che tu conosca Go e le basi di HTTP. Il perché delle scelte è in decisioni e storia.

    i
    Riferimenti al codice. I riferimenti file.go:riga puntano alla versione 1.0. Le funzioni sono sempre citate per nome, così restano rintracciabili anche se le righe si spostano.

    1.2 · Principi

    Sei principi guidano tutte le scelte del codice. Sono decisioni prese e documentate, da non riaprire senza una ragione forte (l'elenco completo è in CLAUDE.md).

    Un solo binario
    Eseguibile statico (CGO_ENABLED=0), nessun programma esterno obbligatorio. Unica libreria: rardecode. Motore di download ed estrazione sono integrati.
    Un resolver per tutti
    I siti XFileSharing condividono lo stesso script lato server: una logica generica con euristiche li copre quasi tutti.
    Solo premium
    Nessun aggiramento di captcha o countdown: se il countdown compare, l'errore lo dice. Scelta etica e di robustezza.
    Robusto sul campo
    Ripresa senza duplicazioni, controllo della dimensione, link scaduti rigenerati, TLS tollerante solo dove serve.
    Test senza rete
    47 test ermetici con server HTTP fittizi; il test dal vivo parte solo se richiesto.
    La documentazione è codice
    make test fallisce se un'opzione o un file non sono documentati o se la versione non coincide.

    Altre decisioni che toccano il codice: niente sottoprocesso scrap (il motore del progetto gemello è stato re-implementato qui, scrap resta intoccato, i nomi delle opzioni sono armonizzati); una barra per file (i premium danno una connessione per file, la vista multi-segmento non serve); TLS con ripiego automatico e mirato (Cap. 6).

    1.3 · Sottosistemi in breve

    Il programma è organizzato in sottosistemi coesi, uno o due file ciascuno. Questa è la mappa che il manuale approfondisce capitolo per capitolo:

    main.go
    Avvio, opzioni, modalità speciali e ciclo a lotti (Cap. 3).
    accounts.go, links.go
    I due file di ingresso e l'abbinamento sito ↔ account (Cap. 4).
    resolver.go
    Login XFileSharing e trasformazione di una pagina-file in link diretto con il nome vero (Cap. 5).
    tls.go
    Ripiego senza verifica solo per le catene di certificati incomplete (Cap. 6).
    download.go, util.go
    Motore di download: sonda, flusso singolo o segmentato, ripresa, tentativi, banda (Cap. 7).
    progress.go, help.go, tui.go, term_*.go
    Barre di avanzamento, guida integrata e TUI (Cap. 8).
    extract.go
    Estrazione RAR/ZIP con password e ripiego sugli strumenti esterni (Cap. 9).
    *_test.go, tools/, Makefile, CI
    Test, controlli della documentazione, build e rilascio (Cap. 10 e Cap. 11).

    1.4 · Mappa dei file

    Tutto il programma è un unico package main. Le righe sono controllate da tools/check-docs.py: se un file cambia lunghezza di più del 10% (con un minimo di 3 righe), o ne compare uno nuovo senza riga qui, make test fallisce (§ 10.4).

    Capitolo 2

    Architettura generale

    2.1 · Componenti

    hoster è un programma a riga di comando a vita breve: parte, lavora sulla lista di link e termina. Non ha stato persistente oltre ai file che scrive (.part, .part.hoster, i file scaricati).

    Il punto chiave è il cookie jar condiviso: il resolver fa il login e ottiene i cookie di sessione; il client di download (newDownloadClient, download.go:63) riceve lo stesso jar (res.jar), quindi scarica con la stessa sessione. Anche lo User-Agent (-U) è lo stesso per entrambi, perché alcuni siti legano la sessione all'UA (TestResolverUsesConfiguredUserAgent lo protegge).

    Resolver e downloader hanno invece client e trasporti distinti: il resolver ha un timeout totale di 90 s, il downloader nessun timeout totale ma timeout su connessione, handshake e intestazioni. Ognuno avvolge il proprio trasporto in un tlsFallbackTransport (Cap. 6).

    2.2 · Un'esecuzione

    Il ciclo in main.go procede a lotti di -j link: risolve tutti i link del lotto in sequenza, lancia un goroutine per file e aspetta la fine dell'intero lotto (sync.WaitGroup) prima di passare al successivo. Così i link diretti vengono generati poco prima dell'uso, perché scadono in fretta. Il rovescio della medaglia: un file lento tiene fermo il lotto successivo (Cap. 13).

    for bi := 0; bi < len(links); bi += *jobs {
	end := min(bi+*jobs, len(links))
	chunk := links[bi:end]

	// Risolvo il lotto (i link diretti scadono: meglio "freschi" appena prima).
	var direct []Resolved
	for _, link := range chunk {
		r, err := res.Resolve(link)
		...
	}
	// Scarico il lotto in parallelo.
	var wg sync.WaitGroup
	...
	wg.Wait()
}

    Prima di lanciare un download, main calcola la destinazione (Name, o fileNameFromURL se vuoto) e la segna in seenDest: un secondo link verso lo stesso file viene saltato come duplicato (main.go:170). La funzione refresh passata al downloader richiama Resolve sul link originale (Resolved.Link) quando il link diretto scade.

    fileNameFromURL prende l'ultimo segmento del percorso, decodificato; se l'URL non si analizza o il segmento è vuoto, / o . restituisce download.bin.

    2.3 · Concorrenza e stato condiviso

    Download, ri-risoluzioni e barre sono concorrenti; per questo i test girano con -race. Questi sono i goroutine che possono esistere insieme e ciò che condividono:

    2.4 · Dove va l'output

    Barre, righe di log e riepilogo del download vanno su stderr; la riga scaricati: N falliti: M, l'uscita di --dry-run e quella dell'estrazione vanno su stdout. Gli errori fatali (fatal, main.go:227) vanno su stderr con il prefisso hoster: e stato 1. Il pacchetto flag esce con stato 2 sulle opzioni sconosciute, stampando la guida in testo semplice su stderr (flag.Usage = usage).

    Capitolo 3

    Avvio e configurazione

    3.1 · La sequenza di avvio

    Tutta la configurazione arriva dalla riga di comando: hoster non legge file di impostazioni né variabili d'ambiente, a parte NO_COLOR, PAGER, le variabili del proxy (http.ProxyFromEnvironment) e quelle dei test (HOSTER_LIVE, HOSTER_ACCOUNT, HOSTER_LINKS).

    1. wantsHelp intercetta -h, -help, --help e help prima di flag.Parse (fino a un eventuale --): displayHelp, poi uscita con stato 0.
    2. flag.Parse legge le opzioni. Il pacchetto flag di Go accetta ogni opzione sia con un trattino sia con due (-dry-run e --dry-run sono la stessa cosa).
    3. Con --extract-only DIR esegue runExtraction e termina: non servono né account né link.
    4. parseSize interpreta --rate; LoadAccounts e LoadLinks leggono i due file. Un errore qui, o una lista vuota, è fatale.
    5. Crea la cartella di destinazione (MkdirAll, anche in --dry-run) e il Resolver.
    6. Con --dry-run risolve ogni link, stampa nome e link diretto e termina.
    7. Altrimenti crea Progress (e lo pubblica in gProg), il client di download e il Downloader, esegue il ciclo a lotti, stampa il riepilogo e, con -e, estrae.

    3.2 · Le opzioni e dove agiscono

    La tabella segue le opzioni dal punto in cui sono definite (main.go) al codice che le usa. Il riferimento per l'utente, con esempi, è nel riferimento delle opzioni del manuale utente.

    i
    Nota. Le 23 righe della guida (helpSections) sono la fonte per la documentazione: TestHelpCoversAllFlags ne verifica il numero e tools/check-docs.py controlla che ognuna abbia la sua voce nel manuale utente.

    3.3 · Dalle opzioni al motore: DLConfig

    Le opzioni del download confluiscono in DLConfig, passato a NewDownloader insieme al client e al Progress:

    dlClient := newDownloadClient(res.jar, *timeout, *split+*jobs, insecure)
dl := NewDownloader(dlClient, DLConfig{
	Split:     *split,
	Jobs:      *jobs,
	MinSplit:  1 << 20,
	Continue:  *cont,
	Retries:   *retries,
	RetryWait: *retryWait,
	Rate:      rate,
	Timeout:   *timeout,
	UserAgent: *ua,
}, prog)

    MinSplit non è un'opzione: è fissato a 1 MiB, sotto il quale un file non viene mai segmentato. I campi Jobs e Timeout sono memorizzati ma il Downloader non li legge: pool di connessioni e timeout sono già applicati da newDownloadClient (Appendice A).

    3.4 · Modalità speciali

    --dry-run usa lo stesso Resolver del download (login, TLS, dump di debug), ma non crea né Progress né Downloader: per ogni link stampa ✓ nome e il link diretto, oppure ✗ link e l'errore; alla fine risolti: N falliti: M. È lo strumento principale per provare un sito nuovo (Cap. 12).

    --extract-only DIR è controllata subito dopo flag.Parse, prima ancora di leggere --rate: estrae e termina (Cap. 9).

    -v aggiunge dopo ogni risoluzione la riga → nome link-diretto, utile per vedere quale link è stato scelto senza lanciare un --dry-run.

    3.5 · Stati di uscita

    !
    Attenzione. La guida integrata descrive lo stato 1 come «errore durante l'esecuzione», ma i download falliti non lo producono: uno script deve leggere la riga scaricati: N falliti: M. È un limite noto (§ 13.1).
    Capitolo 4

    Account e link

    4.1 · Formato di account

    LoadAccounts (accounts.go:45) legge una riga per volta, dopo TrimSpace, e salta righe vuote e commenti #. firstSep trova il primo tra : e ;: il primo separatore chiude il dominio, il secondo l'utente, e la password è tutto il resto, non ripulito (può contenere separatori e spazi interni). Il dominio passa da normHost, l'utente da TrimSpace.

    Se due righe hanno lo stesso host o la stessa etichetta, vince l'ultima: le mappe vengono semplicemente sovrascritte.

    4.2 · Abbinamento host ↔ account

    Ogni account è indicizzato due volte: per host normalizzato (byHost) e per etichetta, la parte prima del primo punto (byLabel). Lookup prova prima l'host esatto, poi l'etichetta: così terabytez:… vale per terabytez.org e terabytez.com.

    normHost (util.go:17) accetta anche un URL intero: minuscolo, toglie schema, percorso, query, frammento, credenziali, porta e www.. Attenzione: labelOf prende la prima etichetta, quindi un sottodominio come fs12.terabytez.org dà fs12. Non è un problema perché il lookup avviene sull'host del link della pagina-file, non su quello dei server di download.

    func (a *Accounts) Lookup(host string) (Account, bool) {
	if acc, ok := a.byHost[normHost(host)]; ok {
		return acc, true
	}
	if acc, ok := a.byLabel[labelOf(host)]; ok {
		return acc, true
	}
	return Account{}, false
}

    4.3 · Formato di links

    LoadLinks (links.go:11) salta righe vuote e commenti, toglie gli spazi ai bordi e deduplica mantenendo l'ordine. Il buffer dello scanner è di 1 MB per riga. Non c'è validazione: un URL non valido viene segnalato da Resolve (URL non valido) e conta come fallito.

    La deduplicazione è sul testo della riga: due link diversi che portano allo stesso file vengono fermati più tardi, da seenDest, solo se producono lo stesso nome di destinazione (§ 2.2).

    Capitolo 5

    Il resolver

    5.1 · Il client del resolver

    Il resolver è il cuore di hoster: fa il login XFileSharing e trasforma una pagina-file in un link diretto, con il nome vero del file.

    NewResolver (resolver.go:33) crea un cookie jar e un http.Client con timeout totale di 90 secondi (fisso, indipendente da --timeout) e trasporto newTLSFallbackTransport (proxy dall'ambiente, HTTP/2 tentato). do imposta User-Agent e Accept e legge al massimo 16 MB di corpo; openFilePage ne legge al massimo 8 MB. Il client segue i redirect (comportamento predefinito di Go) e il jar raccoglie i cookie di ogni passo.

    5.2 · Login

    ensureLogin (resolver.go:142) esegue il login una sola volta per host: la mappa loggedIn è protetta da mu, perché le ri-risoluzioni dei link scaduti avvengono in parallelo. L'host è sempre contattato in https. Se nella pagina di login c'è un campo nascosto token (CSRF), viene inviato. Senza account per l'host l'errore è nessun account nel file 'account' per HOST.

    form := url.Values{}
form.Set("op", "login")
form.Set("login", acc.User)
form.Set("password", acc.Pass)
form.Set("redirect", base+"/")
if tok := extractHidden(page, "token"); tok != "" {
	form.Set("token", tok)
}
res, _, err := r.postForm(base+"/", form, base+"/?op=login")

    looksLoggedIn (resolver.go:187) è un'euristica:

    1. se la pagina contiene incorrect login, wrong password o username and password do not match → fallito;
    2. se contiene op=logout, logout, my account o myaccount → riuscito;
    3. altrimenti riuscito se nel jar c'è un cookie xfss, xfsts, login o con sess nel nome.
    !
    Limite. L'euristica è permissiva: basta la parola «logout» in qualunque punto della pagina, o un cookie di sessione anonima, per dichiarare il login riuscito. Un login in realtà fallito si manifesta dopo, come «countdown rilevato» o «link diretto non trovato».

    5.3 · Risoluzione

    openFilePage (resolver.go:103) apre la pagina-file e decide solo dalle intestazioni: se il Content-Type non è text/html, o c'è un Content-Disposition: attachment, l'host sta già servendo il file (tipico degli account premium, confermato su terabytez e filestore) e il corpo non viene letto. In quel caso Resolve restituisce come URL il link originale: il downloader rifarà la GET con gli stessi cookie e seguirà gli stessi redirect.

    Se la risposta è HTML, Resolve cerca un link diretto nella pagina; se non c'è, esegue fino a tre passi del form di download XFileSharing (op=download1 → op=download2): a ogni passo verifica il countdown, prende il primo <form> che contiene un campo name="op" (extractDownloadForm), lo invia con tutti i suoi <input> (action resa assoluta con resolveURL; senza action, la pagina stessa) e cerca di nuovo il link. Alla fine, se la pagina contiene la parola «premium», l'errore suggerisce un file solo-premium.

    5.4 · Nome del file

    Non tutti gli host mettono il nome nell'URL: terabytez sì (/id/nome.rar), filestore no (solo un id opaco). L'ordine delle fonti:

    nameFromURLPath accetta un segmento solo se ha un'estensione, così un id opaco viene scartato. cleanFileName decodifica le entità HTML, toglie componenti di percorso (anche con \) e punti o spazi ai bordi: un nome come ../../etc/passwd diventa passwd. cdFileName (download.go:458) usa mime.ParseMediaType, preferisce filename* (RFC 5987) e ha un ripiego con espressione regolare per le intestazioni malformate.

    5.5 · Euristiche HTML

    extractDirectLink (resolver.go:405) prova queste espressioni in ordine; vince la prima che trova un link che non sia un asset (.css, .js, /themes/, /images/). Il link trovato viene decodificato dalle entità HTML.

    detectCountdown considera countdown la presenza di id="countdown", countdown_str, please wait, seconds to download o wait_time. Le funzioni di supporto sono in util.go: attr estrae un attributo con virgolette doppie o singole e ne decodifica le entità; extractHidden cerca il valore di un <input> per nome.

    5.6 · Dump di debug

    Con --debug DIR, dump salva le pagine di ogni passo (creando la cartella):

    LINK è il link ridotto da safeName a caratteri alfanumerici e _, al massimo gli ultimi 60.

    Capitolo 6

    Il ripiego TLS

    6.1 · Il problema: catene incomplete

    hoster tollera le catene di certificati incomplete senza rinunciare alla verifica altrove.

    Alcuni server di download (confermato su fsNN.terabytez.org:183, certificato GlobalSign) inviano solo il certificato foglia, senza l'intermedio. I browser completano la catena da soli; crypto/tls di Go no e fallisce con x509: certificate signed by unknown authority. Login e risoluzione passano, cade solo l'handshake con il nodo che serve il file.

    6.2 · tlsFallbackTransport

    tlsFallbackTransport (tls.go:19) tiene due trasporti clonati dallo stesso base, uno con verifica e uno con InsecureSkipVerify:

    1. Con -k usa sempre quello senza verifica.
    2. Se l'host (req.URL.Host, porta compresa) è già noto come «catena incompleta», usa quello senza verifica.
    3. Altrimenti prova con verifica. Solo se l'errore è un x509.UnknownAuthorityError (isIncompleteChain, con errors.As) memorizza l'host, stampa la nota (una volta sola) e ripete la richiesta con un clone senza verifica.
    func (t *tlsFallbackTransport) RoundTrip(req *http.Request) (*http.Response, error) {
	if t.force {
		return t.insecure.RoundTrip(req)
	}
	if _, known := t.bad.Load(req.URL.Host); known {
		return t.insecure.RoundTrip(req)
	}
	resp, err := t.secure.RoundTrip(req)
	if err != nil && isIncompleteChain(err) {
		if _, seen := t.bad.LoadOrStore(req.URL.Host, struct{}{}); !seen {
			notef("nota: %s ha una catena di certificati incompleta — verifica TLS saltata per questo host", req.URL.Host)
		}
		return t.insecure.RoundTrip(req.Clone(req.Context()))
	}
	return resp, err
}

    6.3 · Cosa resta rifiutato

    Scadenza, hostname errato e ogni altro errore restano errori: la deroga vale solo per «autorità sconosciuta» e solo per quell'host. Resolver e downloader hanno ciascuno il proprio trasporto, quindi la nota può comparire una volta per ciascuno. La memoria degli host è per esecuzione: non viene salvata su disco.

    i
    Verificato sul campo. Il set Kali completo (15 volumi, circa 18 GB) è stato scaricato da terabytez senza -k, con il solo ripiego automatico. TestLiveResolve usa apposta force=false.
    Capitolo 7

    Il motore di download

    7.1 · Il client

    Il motore di download è la re-implementazione, dentro hoster, di quello di scrap: sonda, flusso singolo o segmentato, ripresa, tentativi e link scaduti.

    newDownloadClient (download.go:63) condivide il jar del resolver e usa il ripiego TLS. Non ha un timeout totale: un download di molti gigabyte non deve scadere. I timeout di --timeout valgono per la connessione (net.Dialer), l'handshake TLS e l'attesa delle intestazioni di risposta. MaxIdleConns è 100, MaxIdleConnsPerHost è -s + -j.

    base := &http.Transport{
	Proxy:                 http.ProxyFromEnvironment,
	DialContext:           (&net.Dialer{Timeout: time.Duration(timeout) * time.Second}).DialContext,
	TLSHandshakeTimeout:   time.Duration(timeout) * time.Second,
	ResponseHeaderTimeout: time.Duration(timeout) * time.Second,
	ForceAttemptHTTP2:     true,
	MaxIdleConns:          100,
	MaxIdleConnsPerHost:   maxConns,
}
return &http.Client{Transport: newTLSFallbackTransport(base, forceInsecure), Jar: jar}

    7.2 · La sonda

    probe (download.go:105) fa una GET con Range: bytes=0-0:

    Legge e scarta al massimo 64 KB del corpo, così la connessione torna riutilizzabile. Raccoglie anche il Content-Type e il nome dal Content-Disposition (probeInfo).

    7.3 · downloadFile

    downloadFile (download.go:145) coordina un file:

    1. Se la destinazione esiste e -c non è attivo, esce subito con successo (file già scaricato).
    2. Sonda. Se il nome corrente non ha estensione e il server dichiara un nome, la destinazione diventa quel nome.
    3. Sceglie segmented se il server accetta i range, il file è di almeno 1 MiB (MinSplit) e -s > 1; altrimenti singleStream. Scrive sempre su DEST.part e rinomina solo a successo.
    4. Se sonda o download falliscono per un link scaduto, chiama refresh (al massimo maxRefresh = 2 volte), toglie la barra senza contarla come fallimento (cancelFile), stampa nota: link diretto scaduto, lo rigenero e ricomincia dal punto 2.
    func isStaleLink(err error) bool {
	var he *httpError
	if errors.As(err, &he) {
		switch he.code {
		case 401, 403, 404, 410:
			return true
		}
	}
	return false
}

    7.4 · Flusso singolo

    singleStream (download.go:349) è il caso normale (1 connessione per file):

    • Punto di partenza: con -c e range supportati riparte dalla dimensione del .part esistente (se minore del totale, o se il totale è ignoto); altrimenti tronca a zero.
    • A ogni tentativo riparte dall'offset realmente scritto (fp.done), con Range: bytes=N-. Se il server ignora il range e risponde 200, riscrive dall'inizio. Senza range supportati tronca e ricomincia.
    • Scrittura posizionale con WriteAt: niente accodamento, quindi niente byte duplicati. Il test TestDownloadFileResumesAfterMidStreamDrop protegge proprio questo: la vecchia versione accodava e produceva file più grandi e corrotti.
    • Controllo di fine: se la dimensione è nota e lo stream finisce prima, l'errore download incompleto: X/Y byte fa scattare un nuovo tentativo.
    • Stati HTTP: una risposta ≥ 400 diventa httpError; il buffer di lettura è di 64 KB e ogni lettura passa dal limitatore di banda.

    7.5 · Download segmentato

    segmented (download.go:228) divide il file in -s segmenti uguali (makeSegs; l'ultimo prende il resto), prealloca il .part con Truncate e lancia un goroutine per segmento, ognuno con i propri tentativi e Range: bytes=da-a (fetchRange). Ogni 1,5 secondi, e in caso di errore, salva lo stato nel file accanto:

    Con -c lo stato viene ricaricato solo se dimensione e numero di segmenti coincidono (l'URL salvato non viene confrontato). A successo il file di stato viene cancellato e il .part rinominato. Nel flusso singolo il file .part.hoster non esiste: la ripresa usa la dimensione del .part.

    7.6 · Tentativi

    withRetry (download.go:440) esegue la funzione fino a 1 + --retries volte, attendendo --retry-wait secondi tra un tentativo e l'altro. Un errore da link scaduto interrompe subito i tentativi: insistere sullo stesso URL è inutile, ci pensa downloadFile a rigenerarlo.

    func (d *Downloader) withRetry(fn func() error) error {
	var err error
	for attempt := 0; attempt <= d.cfg.Retries; attempt++ {
		if attempt > 0 {
			time.Sleep(time.Duration(d.cfg.RetryWait) * time.Second)
		}
		if err = fn(); err == nil {
			return nil
		}
		if isStaleLink(err) {
			return err // inutile ritentare lo stesso URL scaduto: lo gestisce chi ri-risolve
		}
	}
	return err
}

    Nel download segmentato ogni segmento ha il proprio withRetry: un segmento può ritentare mentre gli altri proseguono.

    7.7 · Limite di banda

    RateLimiter (util.go:122) è un token bucket globale, condiviso da tutti i download, con capacità pari a un secondo di banda. meterReader avvolge ogni corpo di risposta e chiama Take(n) dopo ogni lettura, dormendo se i token sono finiti. Con --rate 0 (predefinito) Take ritorna subito.

    parseSize accetta un numero (anche decimale) con suffisso k/M/G/T (maiuscolo o minuscolo) in potenze di 1024; una stringa vuota vale 0; un valore non numerico dà dimensione non valida, fatale all'avvio.

    Capitolo 8

    Avanzamento e interfaccia a terminale

    8.1 · Barre di avanzamento

    Una barra per file, messaggi che scorrono sopra le barre senza rovinarle, e una guida integrata a schede. Tutto con sequenze ANSI, senza librerie.

    Progress (progress.go:40) tiene l'elenco dei file in corso. Se stderr è un terminale e l'uscita non è silenziata, run ridisegna ogni 120 ms l'area viva: una riga per file più il piede «N in corso · M completati · K falliti». Per ridisegnare risale di liveLines-1 righe (ESC[nA), cancella fino in fondo (ESC[J) e riscrive.

    La velocità è una media mobile esponenziale (0,6 × precedente + 0,4 × istantanea), aggiornata al massimo ogni 100 ms. La barra usa gli ottavi di blocco Unicode (▏▎▍▌▋▊▉) per la frazione. La larghezza è colonne − 74, tra 8 e 28 celle; il nome è troncato (con …) o riempito a 28 caratteri. Senza dimensione nota la percentuale diventa · e manca il tempo residuo.

    8.2 · Messaggi sopra le barre

    I messaggi passano da Log (o notef, progress.go:18, che usa il gProg globale se c'è, altrimenti scrive su stderr): cancellano l'area viva, stampano il messaggio e ridisegnano, così il messaggio resta sopra le barre. Senza terminale, i messaggi sono righe semplici e le barre non ci sono. notef serve ai componenti che non conoscono il Progress: il ripiego TLS e la rigenerazione dei link.

    8.3 · Silenzio e colori

    Con -qe o -qa Progress è quiet: niente barre e nessuna riga di log, compresi gli errori dei singoli file, e nessun riepilogo finale. La differenza tra i due è solo la riga scaricati/falliti in main. NO_COLOR (qualunque valore non vuoto) disattiva i colori; senza terminale i colori sono comunque spenti.

    !
    Differenza dalla guida. La guida integrata dice che -qe mostra «solo gli errori», ma gli errori dei singoli file sono soppressi: restano solo gli errori fatali e il conteggio (§ 13.1).

    8.4 · Guida integrata: una fonte, tre viste

    Il contenuto della guida sta in help.go: helpSections (le opzioni per sezione), supportedHosts, hostsTested, helpExamples, descrizione. Da lì nascono sia la pagina di manuale (buildHelp, con colori ANSI, larghezza tra 60 e 100 colonne) sia le schede della TUI (buildTabs: Info, una scheda per sezione di opzioni, Host, Esempi). TestHelpCoversAllFlags confronta le opzioni con quelle della guida: nessuna mancante, nessuna fantasma.

    wantsHelp intercetta -h, -help, --help e help prima di flag.Parse. displayHelp sceglie:

    1. stdin o stdout non sono terminali → testo semplice senza colori su stdout;
    2. altrimenti la TUI (runTUI); se fallisce (terminale sotto 44×10, o sistema diverso da Linux) →
    3. pagina a colori nel pager: $PAGER (eseguito con sh -c), oppure less -R -F -X, oppure more, oppure stampata così com'è.

    8.5 · La TUI a schede

    La TUI (tui.go) usa lo schermo alternativo (ESC[?1049h), nasconde il cursore e mette stdin in raw mode. Un goroutine legge i byte e parseKeys li traduce in eventi; un ESC isolato vale come uscita. SIGWINCH ridisegna alla nuova dimensione; SIGTERM/SIGHUP escono ripristinando il terminale. La cornice è disegnata con i caratteri di box drawing; l'altezza utile è righe − 6.

    8.6 · Primitive di terminale

    term_linux.go (vincolo di build linux) fornisce termSize (ioctl TIOCGWINSZ su stdout, stderr, stdin e infine /dev/tty, con ripiego 80×24), enterRaw e restoreTerm (ioctl TCGETS/TCSETS: spenti ECHO, ICANON, ISIG, IEXTEN, IXON, ICRNL…, VMIN=1) e i segnali gestiti. term_other.go (!linux) definisce gli stessi simboli: enterRaw fallisce sempre, quindi la guida ripiega sul testo. Queste parti vengono da scrap, il progetto gemello.

    Capitolo 9

    Estrazione

    9.1 · Trovare i set

    Trovare i set di archivi, provare le password, estrarre in sicurezza: tutto con il decoder integrato, con gli strumenti esterni solo come ripiego.

    findArchiveSets (extract.go:214) scorre la cartella (non le sottocartelle) e tiene: ogni .zip; ogni .rar tranne le parti .partN.rar con N diverso da 1 (rePart, zeri iniziali ammessi, maiuscole indifferenti). Il risultato è ordinato. Per il set Kali (15 parti più i .rev) resta solo part01.rar (TestKaliMultiVolumeSet). I volumi vecchio stile .r00, .r01 non sono .rar, quindi resta il solo .rar principale, e rardecode trova da sé i volumi successivi.

    L'estrazione avviene nella stessa cartella degli archivi (-d, o la cartella di --extract-only).

    9.2 · Password e ordine dei tentativi

    buildPasswords costruisce la lista senza duplicati: "", poi -p, poi le righe di --pwfile (vuote e # escluse, \r finali tolti; file assente ignorato). extractSet (extract.go:194) prova tutte le password con il decoder interno e, solo se falliscono tutte, tutte le password con il primo strumento esterno trovato tra rar, unrar, 7z, 7za, 7zz. Il metodo usato finisce nel messaggio (integrato o esterno (TOOL)), insieme a «nessuna password» o «password trovata» (la password non viene stampata).

    9.3 · Decoder interno e strumenti esterni

    • RAR (goExtractRAR): rardecode.OpenReader con l'opzione password; gestisce multi-volume e cifratura. Cartelle create con 0755, file con 0644, sovrascritti se esistono.
    • ZIP (goExtractZIP): archive/zip. Gli ZIP cifrati (bit 0 dei flag) vengono rifiutati e passano allo strumento esterno. La scelta tra i due decoder è per estensione (goExtract).
    • Esterni (extractArgs, runExternal): rar/unrar x -y -o+ -pPW ARCHIVIO DEST/ (-p- senza password); 7z x -y -pPW -oDEST ARCHIVIO. L'uscita dello strumento si vede solo per i tentativi con password.

    9.4 · Sicurezza dei percorsi

    safeJoin (extract.go:49) normalizza il nome (\ → /, Clean("/"+nome)) e verifica che il risultato stia dentro la cartella di destinazione. Grazie alla barra iniziale, un ../../x nell'archivio viene ricondotto dentro la cartella; il controllo finale produce l'errore percorso non sicuro se il percorso uscisse comunque (zip-slip). Vale sia per RAR sia per ZIP; TestGoExtractZIPRoundTripAndSlip verifica che nulla venga scritto fuori.

    func safeJoin(base, name string) (string, error) {
	name = strings.ReplaceAll(name, "\\", "/")
	clean := filepath.Clean("/" + name)
	target := filepath.Join(base, clean)
	root := filepath.Clean(base)
	if target != root && !strings.HasPrefix(target, root+string(os.PathSeparator)) {
		return "", fmt.Errorf("percorso non sicuro nell'archivio: %q", name)
	}
	return target, nil
}

    9.5 · Pulizia

    removeSet ricava la base del set (archiveBase: toglie .partN.rar, .rar o .zip) e cancella nella cartella i file che corrispondono a BASE.(partN.rar|partN.rev|rar|rNN|rev|zip), senza distinzione tra maiuscole e minuscole. Gli altri file (anche con la stessa base, come m.mkv) restano. Avviene solo dopo un'estrazione riuscita.

    Test

    10.1 · La suite

    47 test ermetici, nessuna rete reale e nessuna credenziale, più un test dal vivo che parte solo su richiesta.

    I server sono httptest locali che imitano login, pagine-file, file serviti direttamente, cadute di connessione a metà e link che scadono. Girano con -race perché download, ri-risoluzioni e barre sono concorrenti, e con -count=1 per non usare risultati in cache.

    10.2 · Server fittizi

    Tre attrezzi rendono possibili i test senza rete:

    rewriteRT (resolver_test.go)
    Un RoundTripper che dirotta ogni richiesta https://host/… verso il server di test, conservando percorso, query e intestazioni: così cookie e sessione restano coerenti anche se il resolver crede di parlare con example.test.
    newFakeXFS
    Un sito XFileSharing fittizio: pagina di login con token, POST che accetta solo u/p/tok123, /file-direct che serve un binario con Content-Disposition, /file-html e /dl2 per il percorso a due passi.
    serveData (download_test.go)
    Un server basato su http.ServeContent, quindi con range veri, e un Content-Disposition facoltativo. Il test della caduta a metà usa invece un gestore scritto a mano che interrompe il primo corpo con http.ErrAbortHandler.
    i
    Convenzione. Nei test si usano solo nomi come example.test, h.test, cookie.test: mai dati personali, nemmeno anonimizzati male.

    10.3 · Il test dal vivo

    TestLiveResolve (live_test.go) risolve, senza scaricare, i link reali di LISTA_LINKS con l'account reale, senza -k (verifica così anche il ripiego TLS). Parte solo con HOSTER_LIVE=1 (make live); HOSTER_ACCOUNT e HOSTER_LINKS cambiano i file. Fallisce se nessun link si risolve o se un nome esce vuoto.

    !
    Chi lo lancia. Va eseguito dopo ogni modifica a resolver, login o TLS, ma lo lancia l'utente: le credenziali sono sue e non escono dalla sua macchina.

    10.4 · Controlli della documentazione

    tools/check-docs.py, eseguito da make test (e da solo con make docs-check), quindi anche dalla CI, legge docs/HOSTER_Manuale_Utente.html e docs/HOSTER_Manuale_Tecnico.html e fallisce se:

    • un'opzione di helpSections non ha la sua voce nel riferimento del manuale utente (un <dt data-kind="opzione" data-index="…"> tra id="riferimento" e id="file-usati"), o il manuale documenta un'opzione che non esiste;
    • un file .go manca dalla mappa dei file (la tabella con id="file-map"), la mappa cita un file che non esiste, o il numero di righe indicato si scosta di più del 10% (minimo 3 righe) da quello vero;
    • l'eseguibile ./hoster manca, non è un ELF x86-64 o non contiene la versione di help.go (segno che non è stato rigenerato dopo un cambio di versione);
    • la versione di help.go ("hoster X.Y") non coincide con quella di README.md, docs/index.html e dei due manuali, dove va scritta nella copertina come <span>Versione</span><b>X.Y</b>;
    • un link interno #ancora dei manuali punta a un id che non esiste, o un link da un manuale all'altro (HOSTER_Manuale_Utente.html#ancora) punta a un'ancora assente nell'altro.
    Capitolo 11

    Build, CI e rilascio

    11.1 · Struttura del repository

    !
    File personali. account, links, LISTA_LINKS e passwords.txt sono in .gitignore e non devono mai entrare nel repository, che è pubblico. Sono ignorati anche dbg/ (i dump di --debug contengono pagine viste da utente collegato), downloads/, build/, dist/, *.part, *.part.hoster e *.bundle. Mai git add -A senza guardare.

    11.2 · Build

    $ tools/setup-dev.sh --install
$ make
$ make test
$ make dist

    Su Debian 13 il pacchetto golang-go è già la 1.24. Con un Go più vecchio ma almeno 1.21, la direttiva go 1.24 di go.mod fa scaricare in automatico il toolchain giusto. La prima build scarica rardecode nella cache dei moduli. tools/setup-dev.sh controlla golang-go, build-essential (per gcc), make, python3 e git.

    11.3 · CI e release

    La CI (.github/workflows/ci.yml) gira a ogni push su main, a ogni pull request, a ogni tag v* e su richiesta manuale: installa Go dalla versione di go.mod, esegue make test e make dist e conserva i binari come artefatto. Su un tag v* un secondo job crea la release GitHub con i due binari e SHA256SUMS; il messaggio del tag annotato diventa la descrizione, seguito da istruzioni di scaricamento fisse.

    Per un rilascio:

    1. Aggiorna la versione in help.go ("hoster 1.0"), README.md, docs/index.html e nella copertina dei due manuali. make test controlla che coincidano.
    2. make e registra il nuovo ./hoster (il controllo verifica che contenga la versione).
    3. git tag -a v1.1.0 -m "hoster 1.1.0: …novità…"
    4. git push origin main v1.1.0

    11.4 · Recupero e backup

    Il repository è progettato perché un git clone basti a riavere tutto, tranne i file personali. Il programma pronto è già dentro (./hoster); per ricostruirlo e verificarlo:

    $ git clone https://github.com/nic-fio/HOSTER.git
$ cd HOSTER && tools/setup-dev.sh --install && make test

    tools/setup-dev.sh imposta anche l'identità git locale (nic-fio con l'indirizzo noreply di GitHub; HOSTER_GIT_NAME e HOSTER_GIT_EMAIL la cambiano), che non viene clonata perché sta in .git/config. tools/backup.sh DIR crea hoster-AAAA-MM-GG.bundle, verificato con git bundle verify, e avvisa se ci sono modifiche non registrate o commit non ancora spinti su GitHub. Con --personal aggiunge hoster-personali-AAAA-MM-GG.tar.gz (creato con umask 077): contiene password in chiaro e va tenuto privato. Per l'utente la procedura è descritta nel manuale utente.

    11.5 · I manuali

    I due manuali sono file HTML autonomi: docs/HOSTER_Manuale_Utente.html e docs/HOSTER_Manuale_Tecnico.html. Foglio di stile, diagrammi (SVG disegnati nel documento) e script sono incorporati: nessuna risorsa esterna, nessuna libreria. Si aprono dal clone anche senza rete e si stampano in A4 (copertina su una pagina, un capitolo per pagina, indice laterale nascosto).

    • Ricerca: la casella nella barra laterale (tasto /) filtra le sezioni che contengono tutte le parole cercate, attenua le voci dell'indice che non corrispondono, elenca i risultati con un estratto e, scelto un risultato (o con Invio), porta alla sezione evidenziando le occorrenze. Esc azzera.
    • Indice analitico: generato all'apertura dai termini marcati con l'attributo data-index (più termini separati da ;), raggruppati per iniziale, ognuno con il rimando alla sezione.
    • Senza JavaScript il manuale resta completo e leggibile: la casella di ricerca non compare e l'indice analitico mostra un avviso; l'indice laterale e tutti i collegamenti funzionano.

    Le regole di aggiornamento sono quelle di § 10.4: nuova opzione → riga in helpSections e voce nel riferimento del manuale utente; nuovo file .go → riga nella mappa dei file di questo manuale; nuova versione → copertina di entrambi.

    11.6 · Convenzioni

    • Tutto in italiano: messaggi, commenti, documentazione. I testi rivolti all'utente sono semplici, senza gergo tecnico («copy di prodotto»).
    • Formato: gofmt; go vet pulito.
    • Nessuna nuova dipendenza senza una ragione forte: il binario unico è una scelta di progetto.
    • Ogni correzione nata sul campo ha il suo test di regressione, con un server fittizio.
    • Verificare, non dichiarare: ogni affermazione sul comportamento viene da un'esecuzione (test, --dry-run, download reale).
    • La documentazione si aggiorna insieme al codice: una funzione non è finita finché i manuali non la descrivono.
    • Mai dati personali nel repository: niente credenziali, link personali o dump di debug, nemmeno nei test (usare example.test).
    • Commit con l'identità locale impostata da tools/setup-dev.sh; prima di registrare: make test, make se il codice è cambiato, git status senza file personali.
    Capitolo 12

    Come aggiungere un sito

    12.1 · Il ciclo di lavoro

    Un sito della famiglia XFileSharing spesso funziona senza toccare il codice: basta la riga in account. Quando non basta, il lavoro è quasi sempre in resolver.go.

    1. Aggiungi account e un link, poi make && ./hoster --dry-run --debug dbg.
    2. Login: in login_*_2result.html c'è l'area utente? Se no, guarda il form in login_*_1page.html: nomi dei campi diversi da login/password, un token con altro nome, un captcha (allora il sito non è supportabile). Adegua ensureLogin o looksLoggedIn.
    3. Link diretto: in file_*_N.html cerca dove sta il link al file e aggiungi un'espressione a directLinkREs, nella posizione giusta per la precedenza.
    4. Nome: se il nome esce sbagliato, guarda pageNameREs e fname.
    5. Aggiungi un test in resolver_test.go con un estratto (anonimizzato) della pagina vera, poi make test. Aggiorna l'elenco in help.go (supportedHosts, hostsTested) e le tabelle dei siti nei manuali.

    12.2 · Dove intervenire

    ✓
    Prima di registrare. make test verde, make e registrazione di ./hoster, e un make live lanciato dall'utente con i suoi file reali: il resolver è una delle parti per cui il test dal vivo è obbligatorio.

    Capitolo 15

    Glossario

    15.1 · Termini A–L

    Definizioni dei termini usati nel manuale. I rimandi indicano il capitolo di approfondimento.

    Content-Disposition
    Intestazione HTTP con cui il server indica il nome del file da salvare. Vedi Cap. 5 e 7.
    Catena di certificati
    Foglia → intermedi → radice fidata. Se il server non invia gli intermedi, la catena è incompleta. Vedi Cap. 6.
    Cookie jar
    Il contenitore dei cookie di sessione, condiviso da resolver e downloader. Vedi Cap. 2.
    Countdown
    L'attesa imposta agli utenti gratuiti prima del download. Da premium non compare: se c'è, hoster si ferma. Vedi Cap. 5.
    Git bundle
    Un file che contiene un repository git completo, clonabile senza rete. Vedi Cap. 11.
    Id opaco
    Un codice senza significato al posto del nome del file nell'URL (/nhail4vmw015).
    Link diretto
    L'URL che restituisce il file, di solito su un server di download diverso dal sito e a scadenza breve.
    Lotto
    Gruppo di -j link risolti in sequenza e poi scaricati in parallelo. Vedi Cap. 2.

    15.2 · Termini M–Z

    Pagina-file
    La pagina del sito che corrisponde a un link della lista; da premium spesso serve direttamente il file.
    .part / .part.hoster
    Il file parziale in scrittura e, nel download segmentato, lo stato di ripresa in JSON. Vedi Cap. 7.
    Richiesta Range
    Richiesta HTTP di una parte del file (bytes=da-a); risposta 206 se supportata.
    Ri-risoluzione
    Nuova chiamata a Resolve sul link originale quando il link diretto risulta scaduto (401, 403, 404, 410).
    Sonda
    La richiesta Range: bytes=0-0 con cui il downloader scopre dimensione, supporto ai range e nome. Vedi Cap. 7.
    TUI
    Interfaccia a schede disegnata nel terminale in modalità raw: la guida di --help. Vedi Cap. 8.
    XFileSharing Pro
    Script commerciale per siti di file hosting; molti siti lo usano, con le stesse pagine e gli stessi campi (op=login, op=download1…).
    Zip-slip
    Archivio con nomi come ../../file, costruito per scrivere fuori dalla cartella di estrazione. Vedi Cap. 9.
